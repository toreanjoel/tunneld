What is Tunneld?

Tunneld Device (ARM64 SBC) ┌────────────────────────────────────────────┐ │ upstream NIC ──→ internet │ │ downstream NIC ──→ private subnet (LAN) │ │ │ │ dnsmasq DHCP + DNS ( *.tunneld.lan ) │ │ iptables NAT / forwarding / DNS redirect │ │ Caddy reverse proxy (:18000 + loopback)│ │ WireGuard overlay ( wg-<machine> ) │ │ Phoenix LiveView dashboard │ │ Agent API ( /api/v1/agent ) │ └────────────────────────────────────────────┘ │ │ │ LAN devices enrolled boxes remote VPS (DHCP leases) (local, via SSH) (WireGuard peer)
Self-contained

No database — atomic JSON files under TUNNELD_DATA.

No agent on hosts

Tunneld is the chokepoint — egress policy, audit, scoped tokens. Agents talk over HTTP.

Two installs

WireGuard + Caddy on a target. Anything else is "the operator SSHes in."

Ethernet-first

Wired only; no Wi-Fi mesh, no zrok, no relay coordinator.

The core idea

Tunneld never asks "what runtime is this?" It asks "what is listening?"

Discovery

One command enumerates everything

ss -tlnp lists every listening socket + owning process on any Linux host — Docker, Incus, systemd, a tmux'd binary, or a runtime not yet invented.

{"addr":"0.0.0.0","port":3000,"proc":"node","pid":5678,"container":null}
Two ideas

address, not container

  • Containers remain visible (they listen on ports) but are no longer managed.
  • WireGuard makes remote machines local — one IP tunneld can route to.

Principles that shaped the code

  • Idempotence — every op is ensure_*; re-running converges. No reopen-on-boot logic.
  • Namespace ownership — one tunneld-* namespace per concern per machine.
  • Remote state is authoritative — disk is a hint.
  • Reconcile over repair — one reconcile/1 reads live state and diffs.
  • Delete more than you add — net −766 lines over the refactor.

M1 — Caddy on the gateway

nginx replaced by a Caddy driven entirely through its JSON admin API (no config files, no reload).

sync/1

Reconciles the entire config from the resource list, idempotently. Loaded via POST /load (PUT /config/ 409s on existing config). Per-server automatic_https.disable=true so Caddy never binds :80.

Three planes
  • LAN — :18000, Host-header routed (<name>.tunneld.lan).
  • Loopback — 127.0.0.1:2xxxx per resource, no host matcher (zrok/cloudflared/manual).
  • Public — the machine's own Caddy (M4).

Example resource config

{ "apps": { "http": { "servers": {
  "tunneld_lan": { "listen":[":18000"],
    "routes":[{"match":[{"host":["app.tunneld.lan"]}],
      "handle":[{"handler":"reverse_proxy","upstreams":[{"dial":"10.0.0.5:3000"}]}]}],
    "automatic_https":{"disable":true} },
  "tunneld_123_loop": { "listen":["127.0.0.1:20001"],
    "routes":[{"handle":[{"handler":"reverse_proxy",
      "upstreams":[{"dial":"10.0.0.5:3000"}]}]}],
    "automatic_https":{"disable":true} }
}}}}}

Also: opened :18000 in gateway iptables; installer swaps nginx → Caddy; services monitor keyed off :caddy.

M2 — Runtime discovery

The "what is listening?" generalization. Discovery, not management.

Runtime.listeners/1

Runs ss -tlnp, parses into maps. Annotates the owning container only if a runtime is detected — never gated on one. A bare box works identically to an Incus host.

Surface

Machine detail shows a Listeners panel with a per-row "make resource" action. Backend routed via Overlay.address_for/1.

Example

GET /api/v1/machines/:id/listeners
→ {"listeners":[
    {"addr":"0.0.0.0","port":22,"proc":"sshd","pid":1140,"container":null},
    {"addr":"0.0.0.0","port":3000,"proc":"node","pid":5678,"container":null}
  ]}

M3 — Overlay (WireGuard) + Expose deletion

Overlay
  • Gateway dials out to each machine (PersistentKeepalive=25), one iface wg-<id>.
  • Table = off — routes hand-installed (prevents loops; prerequisite for egress).
  • Keys on the gateway, mode 0600; target only gets its half.
  • address_for/1 — LAN IP same-subnet, overlay IP remote. The single place location is branched.
Deleted

Machines.Expose (SSH -L tunnels) removed — replaced by the overlay. This also removed bugs §3.2 (tunnel leak) and §3.3 (failed exposures persisted). Quick Expose (LAN curl endpoint) kept.

Live-verified acceptance

  • ✓ Resource over overlay serves at http://overlayapp.tunneld.lan:18000, no SSH tunnel.
  • ✓ Reboot-survives — WG iface up with a fresh handshake after gateway reboot, no orphans.
  • setup note: the target needs inbound UDP/51820 open in its provider firewall (e.g. Vultr), not the OS firewall.

M4 — Remote Caddy + public exposure

Mechanism

Drive the machine's own Caddy admin API at http://<overlay_ip>:2019 over WireGuard. Admin bound to the overlay address only — never 0.0.0.0/public.

Caddy.sync_public(machine, resources)
One listen field
listenresult
"8080":8080, no domain/TLS (day one)
"app.example.com":80/:443, auto-TLS

Same object, one field, no migration. Point DNS + change one field.

    match host app.example.com, auto-TLS (default)

M5 — Agent API (the product)

The HTTP API is the product; CLI/skill/MCP are thin adapters.

Tokens / Audit / Jobs
  • AgentTokens — scoped, revocable, hashed-at-rest tnld_.... Forbidden scopes (token issuance, enrollment, iptables admin, DNS provider, WG keys) can never be granted.
  • Audit — append-only JSONL (ts, token_id, action, target, result).
  • Jobs — probe/exec return 202 {job_id}; poll /jobs/:id.
Contract
MethodPathScope
GET/machinesmachines:read
GET/machines/:id/listenersmachines:read
POST/machines/:id/execexec
GET/POST/DELETE/resourcesresources:*
GET/jobs/:idany valid token

Example

POST /api/v1/agent/machines/:id/exec {"cmd":"echo hi"} → 202 {"job_id":"962","status":"running"}
GET  /api/v1/agent/jobs/962 → 200 {"id":"962","status":"done","result":"{...}"}

Live-verified: 200 machines/resources, 201 resource create via real Caddy path, 202 exec → JSON-safe job, 401/403 scope enforcement.

M6 — Egress (per-device exit routing)

gateway exit machine (VM) ip rule add from <device> lookup <N> sysctl ip_forward=1 (persistent) ip route add default dev wg-<id> table <N> iptables -t nat -A POSTROUTING -o <iface> -j MASQUERADE │ device traffic allow forward on wg iface └─────────────► wg-<id> ──────────────► exit ──► internet (as exit's public IP)
  • One ip rule adds a device; one delete removes it. Table IDs persisted, stable across restarts.
  • Works because tunneld is the DHCP default gateway — asserted at runtime with a clear error otherwise.
  • DNS leaks: explicit dns: "exit" | "local" choice, never silent.
Operational caution (learned live)

Only ever route device traffic — never the gateway's own source IP, or you will lock yourself out of the gateway (a policy rule on 10.0.0.1 misroutes management traffic; fix = reboot, since it's runtime-only). Always keep a rollback path.

Setup that must be surfaced (docs/UI)

  • Exit machine: ip_forward=1 persistent, MASQUERADE on egress iface, FORWARD allow on wg iface, and the gateway peer's AllowedIPs must include the LAN subnet.
  • Gateway: routing table per exit + one rule per device.

M7 — Reconcile, Disenroll, UI

Reconcile

reconcile/1 reads live state (WG, Caddy, SSH) and diffs against desired; repair: true idempotently fixes drift. The single live-state authority, replacing ad-hoc reopen-on-boot.

Disenroll

Full reverse teardown: WG config/unit/iface, iptables TUNNELD chain, the tunneld authorized_keys entry, then the registry + key. Live-verified: 0 tunneld artifacts remain on the target.

UI polish

  • Machine detail: Reconcile button + Overlay IP / WireGuard status panel (headless-browser verified, no console errors).
  • Device row: egress dropdown (Local or any exit-capable machine) wired to Egress.route_device.
  • Listeners panel with make resource per row.

M8 — Adapters (CLI → skill → MCP)

Thin adapters over the agent HTTP API; the API is the product.

CLI

mix tunneld.agent

machines, listeners, probe, exec, jobs, resources, add/rm-resource. Uses TUNNELD_URL + TUNNELD_TOKEN.

Skill

skill/tunneld_agent.py

Thin Python client (~95 lines). Verified end-to-end against a live gateway.

MCP

tunneld_mcp.py

MCP JSON-RPC over stdio, 9 tools, one per endpoint, no policy.

Example

mix tunneld.issue_token machines:read,resources:write,exec   # operator mints token
mix tunneld.agent machines
mix tunneld.agent add-resource myapp 10.0.0.5:3000
mix tunneld.agent exec <id> "systemctl status app"

Live-found & fixed during deployment

  • Caddy /load vs /config/ — POST /load (409 on existing config).
  • auto-HTTPS bind :80 — per-server disable=true.
  • iptables blocked :18000 — opened Caddy public port.
  • "any"-scope jobs — authorize_any/1.
  • Job results not JSON-safe — normalized.
  • Egress crypto-routing — exit peer AllowedIPs must include the LAN subnet.

Setup & connection requirements (must be surfaced)

WireGuard overlay (enroll a remote machine)
  • Target reachable over SSH; operator installs tunneld's public key.
  • Inbound UDP/51820 open in the target's provider firewall (e.g. Vultr security group) — NOT the OS firewall.
  • Tunneld installs wireguard-tools, writes configs, brings up wg-quick@wg-<id>.
  • Verify on the target: wg show (handshake), ip -o addr show wg-*.
Public exposure (M4)
  • Install Caddy on the machine; admin API bound to the overlay address only.
  • Open the exposed TCP port in the provider firewall for internet reachability.
  • For auto-TLS: point a hostname's DNS at the machine.
Egress (M6)
  • Exit machine: ip_forward=1 (persistent), MASQUERADE on egress iface, FORWARD allow on wg iface, gateway peer AllowedIPs includes the LAN subnet.
  • Gateway: per-exit routing table + one ip rule per device.
  • Never route the gateway's own IP (lockout risk).
Gateway itself
  • iptables INPUT policy DROP; opens :80, :22, :18000 (Caddy), :5336, DHCP.
  • dnsmasq resolves *.tunneld.lan → gateway.
  • Caddy admin on 127.0.0.1:2019.

How to run & use it

Local dev (no SBC)

MOCK_DATA=true mix phx.server   # full flow on a laptop

Issue a scoped token (operator, on the gateway)

mix tunneld.issue_token machines:read,resources:write,exec

Use the CLI / skill / MCP

export TUNNELD_URL=http://10.0.0.1 TUNNELD_TOKEN=tnld_...
mix tunneld.agent machines
mix tunneld.agent listeners <machine_id>
mix tunneld.agent add-resource web 10.0.0.5:3000

# Python skill
from tunneld_agent import TunneldClient
c = TunneldClient(); print(c.resources())

# MCP (stdio JSON-RPC)
python skill/tunneld_mcp.py

Deploy

scp ~/tunneld_build/tunneld-pre-alpha.tar.gz root@10.0.0.1:/tmp/
ssh root@10.0.0.1 'tar -xzf /tmp/tunneld-pre-alpha.tar.gz -C /opt/tunneld && systemctl restart tunneld'
