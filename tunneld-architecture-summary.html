tunneld

An ethernet-first private network edge relay for ARM single-board computers (Raspberry Pi, NanoPi) — being redesigned from a LAN gateway + WireGuard mesh node into a control plane that SSH-provisions Incus containers on remote machines and exposes them through one dashboard.

1What it is today (verified from the codebase)

Current state

The facts below describe what exists in the tunneld codebase today, verified directly from the source.

  • An Elixir/Phoenix 1.7 application (Elixir 1.18+, OTP 26+), built as a Mix release, no database — all state is atomic JSON files under a data dir.
  • Runs on ARM64 SBCs with two ethernet NICs: one upstream (internet) and one downstream (private subnet). Interface names are selected at install time and read from app config at runtime; never hardcoded. No Wi-Fi.
  • Acts as the LAN gateway for whatever plugs into the downstream port: dnsmasq for DHCP + DNS, iptables for NAT/forwarding/DNS interception, nginx as a reverse proxy listening on 0.0.0.0:18000.
  • Internal DNS is authoritative on the subnet via dnsmasq, resolving names in the .tunneld.lan style. The gateway is the DNS resolver for its subnet.
  • Reverse proxy (nginx) runs on the gateway itself. It serves a static resource registry (resources.json): each resource has a name, a pool of IP:port backends, and is health-checked via TCP probes every 10 seconds. nginx load-balances across healthy backends and each resource is reachable from the subnet at http://<name>.tunneld.lan:18000. There is no public-internet exposure and no per-resource auth.
  • Quick Expose: devices on the subnet can create/list/remove local resources with a single curl. The gateway resolves the caller from its DHCP lease, validates against a per-device allowlist, and provisions a <name>.tunneld.lan hostname.
  • Device management: tracks DHCP leases with online status (ping probe, cached 30s), tagging (tags with the wg prefix advertise a device to the mesh), and lease revocation.
  • LiveView dashboard: real-time, single admin (bcrypt + WebAuthn), first-run setup wizard, offline 2D world map showing peer geolocation by country (inline SVG, no CDN).
  • Supervision tree (current, in Tunneld.Application): Session, SystemResources, Services, Resources, Devices, Auth, DnsConfig, Updater, Wireguard, Geolocation, Mesh, Endpoint.
  • Persistent state files: auth.json, resources.json, mesh_config.json, mesh_node_id.json, wireguard.json, dns_config.json. Writes are atomic (temp + rename) with .bak recovery.

3The redesign: Gateway / subnet role (kept, separated)

Planned / in-progress

This is design intent for the redesign, not yet implemented.

  • The networking role (DHCP, routing) stays as a separate concern from the new control-plane role (SSH provisioning, dashboard). One process handles routing/DHCP; another handles orchestration. They share a box, not state — if the control plane crashes, routing keeps working. This separation is a design goal for the redesign; today they live in one OTP app.

4The redesign: External DNS — a new first-class concept

Planned / in-progress

External DNS is a new concept introduced by the redesign.

  • tunneld.io is the real project/product domain (it does not currently appear anywhere in the repo — the internal domain is tunneld.lan). Under the redesign, external DNS under tunneld.io is how the outside world would find a gateway or its exposed services (e.g. subdomains per gateway or per exposed container). This must be treated as first-class in the new design, not an afterthought config field.
  • Internal DNS (dnsmasq, .tunneld.lan) and external DNS (tunneld.io) are separate systems solving separate problems and must not be collapsed into one "DNS config" concept.

5The redesign: WireGuard mesh — slated for removal

Planned / in-progress

Removal is intended but not yet done — the mesh is still active today.

  • The prompt's claim that the mesh "is now being removed" is aspirational: mesh.ex, wireguard.ex, the wg-mesh interface, relay coordinator client, and iptables mesh forwarding are all still active in the supervision tree right now. The redesign intends to remove them (coordinator, relay, per-peer AllowedIPs, hole-punching) but that work has not been done.

6The redesign: Machine management via SSH — greenfield

Planned / in-progress

Greenfield — no corresponding code exists yet.

  • tunneld would hold or broker SSH access to any number of remote Linux machines — not just one VM, no special-cased "local" machine. Every managed machine is structurally the same: SSH in, provision, register, proxy.
  • Each managed machine should have a dedicated, scoped credential — not a general-purpose root SSH key (ideally restricted to Incus operations via forced command, or Incus's own API/client-cert auth carried over SSH rather than shelling out to incus interactively).
  • On first contact, a capability probe (Incus version, storage, GPU presence) is stored against the machine's record. Capabilities are never assumed.
  • Machine state is treated as remote and authoritative, not cached: tunneld queries live state rather than trusting a local record, because SSH-managed machines drift outside tunneld's view.

7The redesign: Container provisioning — greenfield

Planned / in-progress

Greenfield — no corresponding code exists yet.

  • tunneld would provision "slices" of containers (Incus containers) on managed machines on request.
  • Default target: slim app containers — CPU/memory/port, no special hardware.
  • GPU-backed / streaming workloads (GPU passthrough, Moonlight/Sunshine-style remote desktop) are a structurally different case — different provisioning (device passthrough, driver matching) and a different access path (low-latency direct/LAN, not routed through the same reverse proxy, since tunneling adds latency streaming can't tolerate). Explicitly out of scope for v1.

8The redesign: Reverse proxy (redesigned)

Planned / in-progress

Redesign of the existing proxy — not yet implemented.

  • Still runs on the gateway — the only thing that needs to be externally reachable. Managed machines stay unreachable except through tunneld's SSH connection.
  • The proxy's routing table becomes container ID -> (machine address, port), rebuilt from live state rather than hand-maintained config. (Today the proxy uses a static resources.json registry, not containers.)

9The redesign: Dashboard (redesigned)

Planned / in-progress

Redesign of the existing dashboard — not yet implemented.

  • A single flat view: machines -> containers per machine -> status -> access link.
  • Resist grouping/tagging/environments until there's a real need.
  • "Access" links resolve live at click-time (ask the machine if the container is actually still up, what port it's on) rather than serving a potentially-stale URL.
  • The dashboard is effectively the product: since tunneld owns no compute itself, its value is "one place to see and reach every container across every machine you've handed it SSH access to."

10The redesign: Off-LAN access (optional, deferred)

Planned / in-progress

Optional and deferred — not a v1 requirement.

  • No relay, no mesh, no zrok. If external reachability is wanted without exposing the home connection directly, a single outbound reverse tunnel (e.g. one SSH connection) from the gateway to one VPS you control. Optional, not core. No peer discovery, no coordinator.

11Deliberate non-goals / things cut

Non-goals

Explicitly excluded from scope — present or future.

  • No Zrok/OpenZiti overlay tunnels (original exposure mechanism — already gone).
  • No WireGuard mesh, coordinator, relay, per-peer key exchange (intended to be removed — still in tree today).
  • No "local VM" special case — nothing managed differently because it's physically closer to the gateway. (Note: there was never a VM in the codebase; current scope is DHCP devices on a subnet.)
  • No GPU/streaming support in v1.
  • No control-plane accounts/tokens for third parties — this is a personal/small-group orchestrator, not a multi-tenant hosted service.

12Open design questions

To be resolved explicitly:

  1. Credential model — does the per-machine SSH key grant shell access with Incus commands run as a normal user, or is it scoped to Incus's own API/cert auth carried over SSH? This determines blast radius if a key leaks.
  2. Adding a machine is the single highest-trust action in the system (a total grant, not partial) — should this step in the UI/CLI be made deliberately heavyweight/confirmatory, similar to how a manifest-freeze step is a deliberate, hard-to-miss commitment?
  3. Off-LAN access — is the single reverse tunnel to one VPS a v1 requirement, or purely optional/deferred?
  4. Relationship to other tools — does tunneld's job end at "machine provisioned, container running, reachable via proxy," handing off to a separate tool for what actually runs inside a given container, keeping the two cleanly separated by responsibility?
