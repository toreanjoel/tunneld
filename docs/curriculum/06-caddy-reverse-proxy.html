06 — Caddy Reverse Proxy

Key source: lib/tunneld/caddy.ex, lib/tunneld/servers/resources.ex

What a Reverse Proxy Is

A reverse proxy sits in front of backend servers and forwards client requests to them. Unlike a forward proxy (which clients configure to access the internet), a reverse proxy is transparent to clients — they think they are talking to the proxy, which handles routing to the actual backend.

Reverse proxies provide several benefits: load balancing across multiple backends, TLS termination (handling HTTPS so backends can be plain HTTP), hostname-based routing (multiple services on one port), health checking, request logging, and caching. For Tunneld, the key use is hostname-based routing: a single port 18000 serves all resources, with Caddy routing by the Host header.

Caddy is a modern web server and reverse proxy written in Go. It is notable for automatic HTTPS (via Let's Encrypt ACME), simple configuration, and a JSON admin API that allows runtime reconfiguration without restarts. Tunneld uses Caddy instead of nginx because it requires no config file template or reload signal — changes are atomic HTTP requests.

How Caddy Works

Host Header Routing

When a browser requests http://ollama.tunneld.lan:18000/api/generate, the HTTP request includes a Host: ollama.tunneld.lan header. Caddy matches this header against configured routes and proxies to the corresponding backend. Multiple services share port 18000 by having different hostnames. 

# HTTP request from browser:
GET /api/generate HTTP/1.1
Host: ollama.tunneld.lan
...

# Caddy sees Host: ollama.tunneld.lan
# Looks up the route for that host
# Proxies to backend 10.0.0.50:11434

The Admin API

Caddy's admin API (default http://127.0.0.1:2019) allows you to inspect and modify the running configuration via HTTP. The most common endpoints:

  • GET /config/ — return the current config as JSON
  • POST /load — replace the entire config atomically
  • PUT /config/apps/http/servers/... — modify a specific part
  • DELETE /config/apps/http/servers/... — remove a part
# View current config:
$ curl http://127.0.0.1:2019/config/ | jq .

# Replace entire config:
$ curl -X POST http://127.0.0.1:2019/load \
    -H "Content-Type: application/json" \
    -d @new_config.json

Automatic HTTPS (ACME)

When Caddy sees a hostname (not an IP or port), it automatically provisions a TLS certificate via Let's Encrypt's ACME protocol. This requires the hostname to be publicly resolvable to the Caddy server. Tunneld disables automatic HTTPS on every server it emits — *.tunneld.lan is not publicly resolvable, and there is no public plane that would need a certificate.

How Tunneld Uses Caddy

Tunneld's Caddy configuration is in lib/tunneld/caddy.ex. It implements two "planes" of exposure:

1. LAN Plane

One server listens on 0.0.0.0:18000 and routes by Host header. Every resource gets a <name>.tunneld.lan hostname. 

# From lib/tunneld/caddy.ex:
def build_config(resources) do
  lan_routes = Enum.map(resources, fn r ->
    %{
      "match" => [%{"host" => [lan_hostname(r["name"])]}],
      "handle" => [reverse_proxy(r["pool"])]
    }
  end)

  %{
    "apps" => %{
      "http" => %{
        "servers" => %{
          "tunneld_lan" => %{
            "listen" => [":18000"],
            "routes" => lan_routes,
            "automatic_https" => %{"disable" => true}
          }
        }
      }
    }
  }
end

2. Loopback Plane

Tools like zrok, cloudflared, or manual SSH tunnels do not send the tunneld.lan Host header, so Host-based routing fails. Each resource also gets a loopback listener on a unique port (20000-30000) with no host matcher. 

# From lib/tunneld/caddy.ex:
defp loop_server(r) do
  bind = Config.gateway_ip() || "127.0.0.1"

  %{
    "listen" => ["#{bind}:#{r["loopback_port"]}"],
    "routes" => [%{"handle" => [reverse_proxy(r["pool"])]}],
    "automatic_https" => %{"disable" => true}
  }
end

# A resource "ollama" with loopback_port 20001 can be accessed at:
# - http://ollama.tunneld.lan:18000 (via Host header)
# - http://10.0.0.1:20001 (via loopback port, no Host header needed)

No Public Plane

There is deliberately no public-internet plane. Driving a remote machine's own Caddy over the overlay was written once, wired to nothing, and removed (lib/tunneld/caddy.ex moduledoc). Off-LAN exposure is the operator's job — point zrok, cloudflared, or an SSH forward at the loopback listener above.

The sync Function

sync/1 is the main entry point. It takes the full list of resources, builds the config, and pushes it to Caddy via POST /load. 

# From lib/tunneld/caddy.ex:
def sync(resources) when is_list(resources) do
  config = build_config(resources)

  if mock?() do
    write_mock(config)   # Write to data/caddy/config.json
  else
    push_config(config)  # POST to http://127.0.0.1:2019/load
  end
end

defp push_config(config), do: push_config(config, "http://127.0.0.1:2019/")

defp push_config(config, base_url) do
  body = Jason.encode!(config)

  case HTTPoison.post(base_url <> "load", body, 
         [{"content-type", "application/json"}]) do
    {:ok, %{status_code: 200}} -> :ok
    {:ok, %{status_code: code, body: resp}} -> 
      {:error, {:caddy_http, code, resp}}
    {:error, reason} -> 
      {:error, {:caddy_http, reason}}
  end
end

Why Caddy Over nginx

No Config Files

nginx requires config files in /etc/nginx/sites-available/, symlinks in sites-enabled/, and a reload signal (nginx -s reload). Caddy's admin API means no files and no signal — just an HTTP POST.

No Templates

A templated config generator (EEx rendering an nginx config file) is error-prone: escaping issues, syntax errors, and a reload step that can fail silently. Caddy's JSON API uses Elixir maps that Jason encodes directly.

Automatic HTTPS

Where a deployment does terminate TLS, Caddy handles Let's Encrypt automatically while nginx requires certbot, cron jobs, and manual renewal handling. Tunneld itself never uses this: every server it emits sets "automatic_https" => %{"disable" => true}.

Single Binary

Caddy is one static binary with no dependencies. nginx requires several packages and OpenSSL. This simplifies installation on targets.

Examples

View current Caddy config

$ curl -s http://127.0.0.1:2019/config/ | jq '.apps.http.servers'
{
  "tunneld_lan": {
    "listen": [":18000"],
    "routes": [
      {
        "match": [{"host": ["ollama.tunneld.lan"]}],
        "handle": [{"handler": "reverse_proxy", "upstreams": [{"dial": "10.0.0.50:11434"}]}]
      }
    ]
  },
  "tunneld_abc123_loop": {
    "listen": ["10.0.0.1:20001"],
    "routes": [...]
  }
}

Test a resource endpoint

# Via LAN hostname:
$ curl -H "Host: ollama.tunneld.lan" http://10.0.0.1:18000/api/tags
{"models":[...]}

# Via loopback port:
$ curl http://10.0.0.1:20001/api/tags
{"models":[...]}

Manually update Caddy config

# Get current config, modify it, push it back:
$ curl -s http://127.0.0.1:2019/config/ > caddy.json
$ vim caddy.json  # Make changes
$ curl -X POST http://127.0.0.1:2019/load \
    -H "Content-Type: application/json" \
    -d @caddy.json

# Or patch a specific path:
$ curl -X PATCH "http://127.0.0.1:2019/config/apps/http/servers/tunneld_lan/routes/0/handle/0/upstreams" \
    -H "Content-Type: application/json" \
    -d '[{"dial": "10.0.0.51:11434"}]'

Check Caddy health

# The admin API answers on /config/ — use it as a liveness check:
$ curl -s http://127.0.0.1:2019/config/ >/dev/null && echo OK
OK

# Check if Caddy can reach a backend (via access logs):
$ journalctl -u caddy -f
