09 — Elixir & OTP Supervision

Key source: lib/tunneld/application.ex, lib/tunneld/servers/resources.ex, lib/tunneld/machines.ex

What Elixir and OTP Are

Elixir is a functional programming language that runs on the BEAM virtual machine, the same VM that runs Erlang. The BEAM is designed for concurrent, distributed, fault-tolerant systems — it powers telecom switches, messaging systems, and databases that need to run forever without downtime.

OTP (Open Telecom Platform) is a set of libraries and design principles that come with Erlang/Elixir. The key abstraction is the process: lightweight, isolated units of execution that communicate via message passing. Unlike OS threads, BEAM processes are cheap (you can have millions) and isolated (one crashing does not affect others).

The killer feature is supervision: processes can supervise other processes. If a child crashes, the supervisor restarts it. This enables the "let it crash" philosophy: instead of defensive coding, you write simple code and let the supervisor handle failures.

How OTP Works

Processes

A BEAM process is not an OS process — it is a lightweight execution unit managed by the VM. You can spawn millions of them. Each process has its own heap, mailbox, and runs independently. Processes communicate by sending messages to each other's mailboxes. 

# Spawn a process:
pid = spawn(fn -> 
  receive do
    {:greet, name} -> IO.puts("Hello, #{name}!")
  end
end)

# Send a message:
send(pid, {:greet, "World"})
# Output: Hello, World!

# The process exits after handling the message

GenServer

GenServer is a behavior (like an interface) for processes that need to hold state and handle synchronous/asynchronous calls. Instead of writing raw receive loops, you implement callbacks: init/1, handle_call/3, handle_cast/2, handle_info/2. 

defmodule Counter do
  use GenServer

  # Client API
  def start_link(initial), do: GenServer.start_link(__MODULE__, initial, name: __MODULE__)
  def increment(), do: GenServer.call(__MODULE__, :increment)
  def get(), do: GenServer.call(__MODULE__, :get)

  # Server callbacks
  def init(initial), do: {:ok, initial}

  def handle_call(:increment, _from, count) do
    {:reply, count + 1, count + 1}
  end

  def handle_call(:get, _from, count) do
    {:reply, count, count}
  end
end

Supervision Trees

A supervisor starts and monitors child processes. If a child crashes, the supervisor restarts it according to a strategy:

  • :one_for_one — restart only the crashed child
  • :one_for_all — restart all children if any crashes
  • :rest_for_one — restart the crashed child and all started after it
# Supervision tree definition:
children = [
  {Session, []},
  {Resources, []},
  {Devices, []}
]

opts = [strategy: :one_for_one, name: MyApp.Supervisor]
Supervisor.start_link(children, opts)

# If Resources crashes, only Resources is restarted
# Session and Devices continue running

How Tunneld Uses OTP

The Supervision Tree

Tunneld's supervision tree is defined in lib/tunneld/application.ex. It uses :one_for_one because the GenServers are mostly independent. 

# From lib/tunneld/application.ex:
def start(_type, _args) do
  children = [
    TunneldWeb.Telemetry,
    {Phoenix.PubSub, name: Tunneld.PubSub},
    {Session, []},
    {SystemResources, []},
    {Services, []},
    {Resources, []},
    {Devices, []},
    {Auth, []},
    {DnsConfig, []},
    {Updater, []},
    {Machines, []},
    {Tunneld.AgentTokens, []},
    {Tunneld.Jobs, []},
    {Tunneld.Geolocation, []},
    TunneldWeb.Endpoint
  ]

  opts = [strategy: :one_for_one, name: Tunneld.Supervisor]
  Supervisor.start_link(children, opts)
end

GenServers in Tunneld

Tunneld has several GenServers, each responsible for a specific domain:

  • Session — in-memory auth sessions (TTL-based expiry)
  • Resources — resource registry, Caddy sync, health checks
  • Devices — DHCP lease monitoring, device list
  • Machines — machine registry, probe coordination
  • Jobs — long-running task tracking
# From lib/tunneld/servers/resources.ex (simplified):
defmodule Tunneld.Servers.Resources do
  use GenServer
  @interval 10_000

  def start_link(_), do: GenServer.start_link(__MODULE__, %{}, name: __MODULE__)

  def init(_) do
    if not file_exists?(), do: create_file()
    _ = Caddy.sync(read_file())
    send(self(), :sync)
    {:ok, %{}}
  end

  def handle_info(:sync, state) do
    resources = broadcast_shares()  # Reads, checks health, broadcasts
    :timer.send_after(@interval, :sync)
    {:noreply, Map.put(state, :resources, resources)}
  end
end

Plain Modules vs GenServers

Not everything is a GenServer. Overlay, Egress, Caddy, Reconcile are plain modules with functions. They do not hold state between calls — they read from disk, run commands, and return. This is deliberate: GenServers serialize access, which adds latency. 

# When to use GenServer:
# - You need to hold mutable state across calls
# - You need periodic tasks (schedule with Process.send_after)
# - You need to serialize access to a resource

# When to use a plain module:
# - Stateless transformations
# - Idempotent operations that read from external state
# - Functions that can run concurrently

Why OTP

Fault Tolerance

If the Devices server crashes (e.g., malformed lease file), it restarts automatically. The dashboard continues working; it just shows stale device data until Devices recovers. This is better than the entire application crashing.

Concurrency

Each LiveView connection is its own process. Each WebSocket is its own process. They run concurrently without explicit thread management. The BEAM handles scheduling.

Hot Code Reloading

You can update a running BEAM system without restarting. GenServers can be upgraded in place. This is powerful for systems that need high availability, though Tunneld does not currently use it (full restarts are acceptable).

Examples

View running processes

# In IEx (iex -S mix):
iex> Process.list() |> length()
156

iex> Process.whereis(Tunneld.Servers.Resources)
#PID<0.456.0>

iex> Process.info(Process.whereis(Tunneld.Servers.Resources), :message_queue_len)
{:message_queue_len, 0}

Inspect a GenServer's state

# In IEx:
iex> :sys.get_state(Tunneld.Servers.Resources)
%{resources: [%{"id" => "abc", "name" => "ollama", ...}]}

# This shows the internal state — useful for debugging

Manually restart a GenServer

# Kill and let the supervisor restart it:
iex> Process.exit(Process.whereis(Tunneld.Servers.Devices), :kill)
true

# Check it restarted:
iex> Process.whereis(Tunneld.Servers.Devices)
#PID<0.789.0>  # New PID

# The supervisor restarted it automatically
