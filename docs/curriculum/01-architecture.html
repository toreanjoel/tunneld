01 — Architecture

Key source: lib/tunneld/application.ex, lib/tunneld_web/live/dashboard.ex

What the Architecture Is

Tunneld is an Elixir/Phoenix application that orchestrates several external services to provide gateway functionality. It is not a monolith that does everything itself — it drives dnsmasq for DHCP/DNS, Caddy for reverse proxying, iptables for firewalling and NAT, and WireGuard for encrypted tunnels. The Elixir application is the control plane that coordinates these components and presents a unified interface via the LiveView dashboard.

The application runs on the BEAM virtual machine, which provides lightweight processes, supervision trees for fault tolerance, and hot code reloading. Phoenix provides the web framework, and LiveView enables real-time updates without writing JavaScript. State is persisted to JSON files on disk (no database), and PubSub broadcasts changes to connected dashboards.

Supervision Tree

The supervision tree is defined in lib/tunneld/application.ex. It uses a flat one_for_one strategy: if a child process crashes, only that child is restarted. This is appropriate because the GenServers are mostly independent — a crash in Devices should not take down Resources. 

# From lib/tunneld/application.ex (simplified):
children = [
  TunneldWeb.Telemetry,
  {DNSCluster, query: Application.get_env(:tunneld, :dns_cluster_query) || :ignore},
  {Phoenix.PubSub, name: Tunneld.PubSub},
  {Session, []},
  {SystemResources, []},
  {Services, []},
  {Resources, []},
  {Devices, []},
  {Auth, []},
  {DnsConfig, []},
  {Updater, []},
  {Tunneld.AgentTokens, []},
  {Tunneld.Jobs, []},
  {Tunneld.Geolocation, []},
  TunneldWeb.Endpoint
]

opts = [strategy: :one_for_one, name: Tunneld.Supervisor]
Supervisor.start_link(children, opts)

The Iptables.reset() call happens outside the supervision tree, at application start (production only). This is deliberate — firewall rules are set once and do not need a GenServer to maintain them.

Request Lifecycle

Let us trace what happens when you click "Make Exit Node" for a machine in the dashboard:

  1. Browser → Phoenix Endpoint
    The dashboard is a LiveView mounted at /. When you click the button, the browser sends a message over the existing WebSocket connection. Phoenix routes it to the handle_event("make_exit_node", %{"id" => id}, socket) callback in dashboard.ex.
  2. LiveView → Egress Module
    The handler calls Tunneld.Egress.ensure_exit_capable(machine). This is a plain Elixir module, not a GenServer — it runs in the LiveView process.
  3. Egress → SSH
    ensure_exit_capable/1 needs to run commands on the machine. It calls Tunneld.Machines.SSH.run(machine, "sysctl -w net.ipv4.ip_forward=1 ..."). SSH uses System.cmd/3 to shell out to the ssh binary.
  4. SSH → Target Machine
    The SSH command runs on the target, enabling IP forwarding and adding iptables rules. Output is captured and returned to Elixir as {:ok, output}.
  5. Egress → Persistence
    If successful, egress.ex allocates a routing table ID for this machine and writes it to egress_tables.json via Tunneld.Persistence.
  6. Machines → PubSub
    Tunneld.Machines.broadcast/2 publishes on the "component:machines" topic. The payload is a map: %{id: "machines", event: :updated, data: machine}.
  7. PubSub → All Dashboards
    Every connected dashboard is subscribed to that topic. Their handle_info(%{id: "machines"} = msg, socket) callback receives the update and re-renders the machine list.
  8. LiveView → Browser
    Phoenix calculates the diff between the old and new HTML, serializes it, and sends it over the WebSocket. The browser's LiveView JS library patches the DOM. The machine now shows "Exit Node: Yes". 
# The data flow, visualized:
Browser (WebSocket) → Phoenix Endpoint → LiveView (handle_event)
  → Egress.ensure_exit_capable/1
    → SSH.run/2 → System.cmd("ssh", [...])
      → Target machine (sysctl, iptables)
    → Persistence.write_json/2
  → PubSub.broadcast/3
    → All LiveView subscribers (handle_info)
      → assign/2, diff, send over WebSocket
        → Browser (DOM patch)

Why This Design

Plain Modules Over GenServers

Many modules that look like they might need a GenServer are actually plain modules: Overlay, Egress, Caddy, Reconcile, Iptables. This is deliberate.

A GenServer is appropriate when you need to hold mutable state across calls or serialize access to a shared resource. But Egress.route_device/3 does not need either — it reads from disk, shells out to ip rule, writes to disk, and returns. If two concurrent calls race, they converge to the same state (idempotence). Wrapping this in a GenServer would serialize operations unnecessarily, adding latency.

JSON on Disk, No Database

Tunneld does not use PostgreSQL, SQLite, or any database. State is JSON files under /var/lib/tunneld/ (or data/ in dev). This is intentional:

  • A dedicated database adds operational complexity on an SBC with limited resources.
  • The data is small (a few hundred machines at most) and reads are infrequent.
  • Atomic writes with backup (write to temp, rename) are enough for durability.
  • The real source of truth is the remote machines anyway — disk is just a hint.

PubSub for Real-Time Updates

When a device gets a DHCP lease, all connected dashboards should see it immediately. This is done via Phoenix PubSub: the Devices server broadcasts on the "component:devices" topic, and every subscribed LiveView receives the update and re-renders.

Concrete Example: Resource Creation

Here is the flow when you create a resource (expose a listener): 

# 1. User picks a discovered listener and clicks "Create Resource"
# Browser sends the "make_listener_resource" event with
# %{"machine_id" => id, "addr" => addr, "port" => port, "proc" => proc}

# 2. LiveView handler (in dashboard.ex):
def handle_event("make_listener_resource",
      %{"machine_id" => id, "addr" => addr, "port" => port, "proc" => proc}, socket) do
  name = sanitize_resource_name("#{proc}-#{port}")

  # Route to the address tunneld can actually reach: LAN IP for a same-subnet
  # machine, overlay IP for a remote one - never the raw bind address.
  backend_addr =
    case Tunneld.Machines.get(id) do
      {:ok, machine} -> Tunneld.Overlay.address_for(machine)
      _ -> addr
    end

  _ = Tunneld.Servers.Resources.add_share(%{
    "name" => name,
    "pool" => ["#{backend_addr}:#{port}"],
    "expose_source" => "listener",
    "expose_machine_id" => id
  })

  {:noreply, socket}
end

# 3. Resources server (servers/resources.ex), handle_call({:add_share, resource}, ...):
resources = read_file()

new_resource =
  resource
  |> Map.put("ip", @gateway_ip)
  |> Map.put("port", @lan_port)
  |> Map.put("pool", normalize_pool(resource))
  |> Map.put("loopback_port", allocate_loopback_port(resources))
  |> Map.merge(%{"id" => ..., "kind" => "host"})

with :ok <- Tunneld.Persistence.write_json(path(), resources ++ [new_resource]),
     :ok <- Caddy.sync(resources ++ [new_resource]) do
  # Broadcast update on "component:resources"
  broadcast_shares()
end
