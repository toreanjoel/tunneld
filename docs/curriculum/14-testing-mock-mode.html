14 — Testing & Mock Mode

Key source: lib/tunneld/machines/ssh.ex, test/tunneld/overlay_test.exs, config/test.exs

What Mock Mode Is

Mock mode (MOCK_DATA=true) allows Tunneld to run on a development machine without real hardware or SSH targets. System commands (iptables, systemctl, ssh) are stubbed, and fake data is provided for DHCP leases, ethernet link state, and machine probes.

This enables development on macOS or any Linux workstation without an SBC. The full enroll → probe → expose flow works, just with simulated responses. The dashboard is fully functional, you just cannot actually route packets.

ExUnit is Elixir's testing framework. Tunneld's tests use mock mode to verify business logic without needing real machines. Tests cover machine enrollment, overlay IP allocation, egress routing, and API endpoints.

How Mock Mode Works

Compile-Time Config

The @mock attribute is set at compile time from app config: 

# In lib/tunneld/overlay.ex:
@mock Application.compile_env(:tunneld, :mock_data, false)

def ensure_peer(machine) do
  if @mock do
    {:ok, %{overlay_ip: mock_overlay_ip(machine)}}
  else
    real_ensure_peer(machine)
  end
end

Fake SSH Responses

lib/tunneld/machines/ssh/mock.ex provides a fake SSH target that responds to commands with simulated output: 

# From lib/tunneld/machines/ssh/mock.ex (simplified):
def run(_machine, "ss -tlnp" <> _, _opts) do

  LISTEN 0      128    0.0.0.0:8080       0.0.0.0:*         users:(("nginx",pid=2))
  """}
end

def run(_machine, "cat /etc/os-release" <> _, _opts) do
  {:ok, "PRETTY_NAME=\"Debian GNU/Linux 12\""}
end

How Tunneld Tests

Test Configuration

config/test.exs enables mock mode and sets test-specific paths: 

# config/test.exs:
import Config

config :tunneld,
  mock_data: true,
  fs_root: "test/tmp"

config :tunneld, TunneldWeb.Endpoint,
  server: false  # Don't start HTTP server in tests

Example Test: Overlay IP Allocation

# From test/tunneld/overlay_test.exs:
defmodule Tunneld.OverlayTest do
  use ExUnit.Case, async: false  # Modifies app env

  alias Tunneld.Overlay

  setup do
    # Clean up overlay.json before each test
    File.rm_rf("test/tmp/overlay.json")
    :ok
  end

  test "ensure_peer allocates overlay IP" do
    machine = %{"id" => "test-123", "address" => "45.76.183.185"}

    assert {:ok, %{overlay_ip: ip}} = Overlay.ensure_peer(machine)
    assert ip =~ ~r/^10\.88\.0\.\d+$/

    # Second call returns same IP (idempotent)
    assert {:ok, %{overlay_ip: ^ip}} = Overlay.ensure_peer(machine)
  end

  test "address_for returns overlay IP for remote machine" do
    machine = %{"id" => "test-456", "address" => "45.76.183.185"}
    Overlay.ensure_peer(machine)

    addr = Overlay.address_for(machine)
    assert addr =~ ~r/^10\.88\.0\.\d+$/
  end
end

Example Test: Runtime Listener Parsing

# From test/tunneld/machines/runtime_test.exs:
test "parse_listeners extracts address, port, and process" do
  ss_output = """
  State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
  LISTEN 0      128    0.0.0.0:80         0.0.0.0:*         users:(("nginx",pid=1234,fd=6))
  LISTEN 0      128    127.0.0.1:5432     0.0.0.0:*         users:(("postgres",pid=5678,fd=5))
  """

  listeners = Runtime.parse_listeners(ss_output, %{})

  assert length(listeners) == 2
  assert Enum.find(listeners, &(&1["port"] == 80))["proc"] == "nginx"
  assert Enum.find(listeners, &(&1["port"] == 5432))["addr"] == "127.0.0.1"
end

Why Mock Mode

Development Without Hardware

You do not need an SBC to develop Tunneld. Run mix phx.server on a MacBook and the dashboard works. This makes onboarding new contributors easier. The full enrollment-probe-expose flow runs on a laptop, complete with fake DHCP leases, simulated SSH responses, and working LiveView updates.

Fast Tests

Tests that SSH to real machines take seconds per command. Mock tests complete in milliseconds. The CI can run the full test suite quickly. A single SSH.run/2 call takes ~1 second to a real machine (TCP handshake, key exchange, authentication, command execution, response). The mock returns instantly from in-memory data.

Deterministic Results

Real machines have varying state. Mock responses are predictable, so tests do not flake due to network issues or changed machine state. A test that expects nginx on port 80 will always see it in mock mode, even if someone reconfigured the real machine.

What Mock Mode Does NOT Cover

Here is the hard truth: mock mode gives you fast, deterministic tests, but it does not prove the system works. Many tests assert only on mock constants — they verify the mock returns what the mock was told to return, which is a tautology.

A code audit reveals significant gaps:

  • Overlay's real key exchange — ensure_peer/1 in mock mode returns a fake overlay IP. No test runs wg genkey, pushes config over SSH, or verifies a handshake actually completes. The real exchange logic in exchange_keys/1 and configure_gateway/3 is untested.
  • Egress's real ip rule/route — route_device/3 in mock mode tracks state in memory and never touches ip rule or ip route. The actual routing table manipulation, including the critical add_default_route/3 and add_forward_rules/1 functions, runs only in production.
  • Disenroll.teardown_remote — The disenrollment flow removes WireGuard configs, Caddy routes, and SSH keys from targets. In mock mode, these are just map deletions. The real SSH commands that delete /etc/wireguard/wg-*.conf on targets are never executed.

How to Tell a Real Test from a Tautological One

A tautological test looks like this: 

test "ensure_peer returns overlay IP" do
  machine = %{"id" => "test-123", "address" => "45.76.183.185"}
  assert {:ok, %{overlay_ip: ip}} = Overlay.ensure_peer(machine)
  assert ip =~ ~r/^10\.88\.0\.\d+$/
end
# This passes because mock_overlay_ip/1 generates "10.88.0.N"
# It does NOT test WireGuard installation or handshakes

A meaningful test verifies behavior that could break: 

test "parse_listeners handles IPv6 addresses" do
  ss_output = "LISTEN 0 128 [::]:80 [::]:* users:..."
  listeners = Runtime.parse_listeners(ss_output, %{})
  assert Enum.find(listeners, &(&1["port"] == 80))["addr"] == "[::]"
end
# This tests the PARSER, which runs the same in mock and prod
# If the regex breaks, this test fails

The distinction: meaningful tests verify logic that runs the same in both modes (parsing, data transformation, allocation algorithms). Tautological tests verify that the mock stub returns the expected stub value.

Examples

Run tests

# Run all tests:
$ mix test

# Run a specific test file:
$ mix test test/tunneld/overlay_test.exs

# Run with verbose output:
$ mix test --trace

Run in mock mode for development

# This is the default in dev:
$ mix phx.server
# Dashboard at http://localhost:80

# Explicitly set mock mode:
$ MOCK_DATA=true mix phx.server

Debug a failing test

# Add IO.inspect to see values:
test "something" do
  result = MyModule.function()
  IO.inspect(result, label: "result")
  assert result == expected
end

# Or use IEx.pry:
test "something" do
  require IEx
  IEx.pry()  # Pauses here, opens IEx
  assert true
end

What mock mode does NOT test

# These require real hardware/machines:
- Actual packet routing through iptables
- Real WireGuard handshakes
- Real SSH connections
- Real DHCP lease assignment
- Actual Caddy proxying

# Tests verify:
- Data parsing (ss -tlnp output, lease files)
- State management (overlay IP allocation)
- API contract (endpoints return expected shapes)
- Business logic (egress table allocation)
