11 — Persistence & State

Key source: lib/tunneld/persistence.ex, lib/tunneld/reconcile.ex

What Persistence Is

Persistence is how an application saves state across restarts. Most applications use databases (PostgreSQL, SQLite) to store data durably. Tunneld takes a simpler approach: JSON files on disk. Each domain has its own file: machines.json, resources.json, auth.json, etc.

The key principle is: remote state is authoritative, disk is a hint. The machines themselves know what is running (via ss -tlnp). Tunneld's JSON files record what was configured, but reconciliation reads live state and converges toward it.

This model trades query flexibility for simplicity. You cannot do complex queries across data. But the data is small (hundreds of records at most), reads are infrequent, and the operational complexity of a database on a resource-constrained SBC is avoided.

How JSON Persistence Works

Atomic Writes

A naive File.write! can corrupt data: if the process crashes mid-write, the file is truncated. Tunneld uses atomic writes: write to a temp file, then rename. The rename is atomic on POSIX filesystems — either the old or new file exists, never a partial write. 

# From lib/tunneld/persistence.ex:
def write_json(path, data) do
  encoded = Jason.encode!(data)
  tmp_path = path <> ".tmp"
  backup_path = path <> ".bak"

  # Backup current file if it exists
  if File.exists?(path) do
    File.copy(path, backup_path)
  end

  # Write to temp file, then atomic rename
  case File.write(tmp_path, encoded) do
    :ok ->
      File.rename(tmp_path, path)
    {:error, reason} ->
      File.rm(tmp_path)
      {:error, reason}
  end
end

Backup Recovery

On read, if the main file is missing or corrupted, read_json/1 falls back to the .bak file. This handles cases where the main file is empty (disk full) or contains invalid JSON (cosmic ray?). 

# From lib/tunneld/persistence.ex:
def read_json(path) do
  case read_and_decode(path) do
    {:ok, data} -> {:ok, data}
    {:error, _} ->
      backup = path <> ".bak"
      case read_and_decode(backup) do
        {:ok, data} ->
          File.copy(backup, path)  # Restore from backup
          {:ok, data}
        error -> error
      end
  end
end

How Tunneld Uses Persistence

Reading State at Startup

GenServers load their state in init/1 by reading from disk: 

# From a typical GenServer:
def init(_) do
  state = %{
    resources: load_resources(),
    last_check: nil
  }
  {:ok, state}
end

defp load_resources do
  # resources.json is a bare JSON array, not a wrapped object.
  case Persistence.read_json(Path.join(Config.fs_root(), "resources.json")) do
    {:ok, list} when is_list(list) -> list
    _ -> []
  end
end

Writing State on Change

When state changes (e.g., resource created), the GenServer writes immediately: 

def handle_call({:create, params}, _from, state) do
  new_resource = Map.put(params, "id", UUID.uuid4())
  new_list = [new_resource | state.resources]

  write_resources(new_list)   # Persist to disk
  Caddy.sync(new_list)        # Update Caddy config
  broadcast(:resources_update, new_list)

  {:reply, {:ok, new_resource}, %{state | resources: new_list}}
end

defp write_resources(list) do
  # Written as a top-level array. (machines.json, by contrast, IS wrapped:
  # %{"machines" => [...]} — see lib/tunneld/machines/store.ex.)
  Persistence.write_json(
    Path.join(Config.fs_root(), "resources.json"),
    list
  )
end

Reconciliation

lib/tunneld/reconcile.ex reads live state from machines and compares against what Tunneld expects. This handles drift (manual changes on the machine) and recovery (after a crash). 

# From lib/tunneld/reconcile.ex:
def reconcile(machine, opts \\ []) do
  repair? = Keyword.get(opts, :repair, false)

  %{
    wireguard: reconcile_wireguard(machine, repair?),
    caddy: reconcile_caddy(machine, repair?),
    ssh: reconcile_ssh(machine),
    resources: reconcile_resources(machine)
  }
end

defp reconcile_wireguard(machine, repair?) do
  # Local machines have no overlay peer — short-circuit before probing.
  if machine["location"] == "local" do
    :ok
  else
    do_reconcile_wireguard(machine, repair?)
  end
end

defp do_reconcile_wireguard(machine, repair?) do
  case Overlay.status(machine) do
    {:ok, %{up: true}} -> :ok
    _ ->
      if repair? do
        case Overlay.ensure_peer(machine) do
          {:ok, _} -> {:repaired, :wireguard}
          {:error, reason} -> {:drift, {:wireguard_down, reason}}
        end
      else
        {:drift, :wireguard_down}
      end
  end
end

Why JSON Files

No Database Complexity

A database adds operational burden: backups, migrations, connection pooling, crash recovery. On an SBC with 2GB RAM, SQLite or PostgreSQL would compete with the application for resources. You would need to configure WAL mode, set up vacuum schedules, and handle migration failures gracefully.

PostgreSQL in particular requires a separate process (the postmaster) that consumes memory even when idle. SQLite is lighter but still requires careful handling of concurrent writes. JSON files with atomic rename have no concurrency issues because each write is a complete replacement of the file contents.

Human-Readable

JSON files can be inspected with cat and edited with a text editor. This is useful for debugging and manual recovery. When something goes wrong, you can SSH into the gateway, open resources.json in vim, and see exactly what the system thinks is configured. You can fix a typo, restart, and be done.

Try doing that with a PostgreSQL database. You would need to connect with psql, write SQL queries, and hope you understand the schema. The JSON approach makes the state completely transparent to operators.

The Data Is Small

A fleet of 100 machines is ~50KB of JSON. There is no performance reason for a database. Parsing 50KB takes milliseconds, and it happens only at startup and on writes. The overhead of a database connection pool would exceed the time saved on reads.

Remote State Is Authoritative

The most important reason is philosophical: disk state is a hint, not the truth. The real source of truth is the machines themselves. A machine knows what processes it is running via ss -tlnp. Tunneld's JSON records what was configured, but reconciliation always reads live state and converges toward it. If the JSON file is lost, Tunneld can re-probe machines and reconstruct most of the state.

This is different from an application where the database IS the truth. An e-commerce site cannot reconstruct orders from external systems. Tunneld can, because the external systems (the machines) have the real state.

Examples

View persisted state

# On the gateway:
$ cat /var/lib/tunneld/resources.json | jq .
[
  {"id": "abc123", "name": "ollama", "pool": ["10.0.0.50:11434"],
   "loopback_port": 20000, "kind": "host"}
]

$ cat /var/lib/tunneld/machines.json | jq '.machines[0]'
{
  "id": "def456",
  "name": "NUC",
  "address": "10.0.0.50",
  "ssh_port": 22,
  "location": "local"
}

Manually fix corrupted state

# If a JSON file is corrupted, restore from backup:
$ cp /var/lib/tunneld/resources.json.bak /var/lib/tunneld/resources.json

# Or manually fix and restart:
$ vim /var/lib/tunneld/resources.json
$ systemctl restart tunneld

Force reconciliation

# In IEx:
iex> {:ok, machine} = Tunneld.Machines.get("def456")
iex> Tunneld.Reconcile.reconcile(machine, repair: true)
%{wireguard: :ok, caddy: :ok, ssh: :ok, resources: :ok}

# Or if something is broken:
%{wireguard: {:repaired, :wireguard}, ...}
