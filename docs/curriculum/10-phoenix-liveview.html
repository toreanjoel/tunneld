10 — Phoenix LiveView

Key source: lib/tunneld_web/live/dashboard.ex, lib/tunneld_web/router.ex

What LiveView Is

Phoenix LiveView is a framework for building real-time, interactive web applications without writing JavaScript. The server renders HTML, sends it to the browser over a WebSocket, and when state changes, sends only the diff. User events (clicks, form submissions) are sent back over the same WebSocket, handled on the server, and the UI updates instantly.

This model inverts the typical SPA architecture. Instead of a JSON API + JavaScript frontend, you write Elixir functions that return HTML. State lives on the server. Interactivity is achieved through event handlers. The result is simpler code and faster development, at the cost of requiring a persistent WebSocket connection.

For Tunneld, LiveView enables a real-time dashboard where device lists, machine statuses, and resource health update automatically as the system state changes. PubSub broadcasts trigger re-renders, and users see updates without refreshing.

How LiveView Works

The Lifecycle

A LiveView goes through several phases:

  1. HTTP GET — initial page load, mounts the LiveView, renders static HTML
  2. WebSocket connect — browser upgrades to WebSocket, LiveView re-mounts
  3. Live updates — events from user or PubSub trigger re-renders
  4. Termination — user navigates away, WebSocket closes
defmodule MyAppWeb.DashboardLive do
  use Phoenix.LiveView

  # Called on HTTP GET and WebSocket connect
  def mount(_params, _session, socket) do
    if connected?(socket) do
      # WebSocket is connected, subscribe to updates
      Phoenix.PubSub.subscribe(MyApp.PubSub, "updates")
    end

    {:ok, assign(socket, count: 0)}
  end

  # Renders HTML
  def render(assigns) do
    ~H"""
    
    """
  end

  # Handles user click
  def handle_event("increment", _params, socket) do
    {:noreply, assign(socket, count: socket.assigns.count + 1)}
  end

  # Handles PubSub broadcast
  def handle_info({:update, new_count}, socket) do
    {:noreply, assign(socket, count: new_count)}
  end
end

Assigns and Diffs

State is stored in the socket's assigns map. When you call assign(socket, key: value), LiveView tracks the change. On re-render, it computes the HTML diff and sends only the changed parts to the browser — not the entire page. 

# Assigning state:
socket = assign(socket, count: 5)
socket = assign(socket, users: ["Alice", "Bob"])

# Accessing in templates:
@count      # 5
@users      # ["Alice", "Bob"]

# Diff sent to browser might be just:
# {"s": ["5"], "p": {"0": "5"}}  (the changed number)

PubSub Integration

When a GenServer updates state, it broadcasts via PubSub. All subscribed LiveViews receive the message in handle_info/2, update their assigns, and re-render. This is how device lists update in real-time across all connected dashboards. 

# GenServer broadcasts:
Phoenix.PubSub.broadcast(Tunneld.PubSub, "component:devices", {:devices_update, devices})

# LiveView receives:
def handle_info({:devices_update, devices}, socket) do
  {:noreply, assign(socket, devices: devices)}
end

How Tunneld Uses LiveView

The Dashboard

lib/tunneld_web/live/dashboard.ex is the main LiveView. It subscribes to multiple PubSub topics on mount and routes updates to child components. 

# From lib/tunneld_web/live/dashboard.ex (simplified):
def mount(_params, session, socket) do
  if connected?(socket) do
    Phoenix.PubSub.subscribe(Tunneld.PubSub, "component:devices")
    Phoenix.PubSub.subscribe(Tunneld.PubSub, "component:resources")
    Phoenix.PubSub.subscribe(Tunneld.PubSub, "component:machines")
    Phoenix.PubSub.subscribe(Tunneld.PubSub, "component:services")
    Phoenix.PubSub.subscribe(Tunneld.PubSub, "notifications")
  end

  {:ok, assign(socket, 
    devices: Devices.list(),
    resources: Resources.list(),
    machines: Machines.list()
  )}
end

def handle_info({:devices_update, devices}, socket) do
  send_update(DevicesComponent, id: "devices", devices: devices)
  {:noreply, socket}
end

Event Handling

User actions like "Create Resource" trigger handle_event/3 callbacks. The handler calls backend modules, updates state, and returns the new socket. 

# From dashboard.ex:
def handle_event("create_resource", %{"name" => name, "port" => port}, socket) do
  machine = socket.assigns.selected_machine
  backend = "#{Overlay.address_for(machine)}:#{port}"

  case Resources.create_resource(%{"name" => name, "pool" => [backend]}) do
    {:ok, _} -> 
      {:noreply, put_flash(socket, :info, "Resource created")}
    {:error, reason} -> 
      {:noreply, put_flash(socket, :error, reason)}
  end
end

def handle_event("make_exit_node", %{"id" => id}, socket) do
  machine = Machines.get(id)
  Egress.ensure_exit_capable(machine)
  {:noreply, socket}
end

Components

Large LiveViews are split into components. Function components are stateless (like React functional components). Live components have their own state and lifecycle. 

# Function component (in dashboard.ex or a separate module):
def device_row(assigns) do
  ~H"""
  
    <%= @device.hostname %>
    <%= @device.ip %>
    <%= @device.mac %>
  
  """
end

# Usage:
<.device_row device={device} />

# Live component (has its own process):
defmodule MachineDetailComponent do
  use Phoenix.LiveComponent

  def update(assigns, socket) do
    {:ok, assign(socket, assigns)}
  end

  def render(assigns) do
    ~H"
Machine: <%= @machine.name %>
"
  end
end

Why LiveView

Real-Time Without Polling

Traditional dashboards poll the server every N seconds. LiveView uses push: when a device gets a DHCP lease, the server broadcasts immediately and all dashboards update. No wasted requests, no stale data. This is fundamentally different from REST APIs where the client must repeatedly ask "has anything changed?" every few seconds, wasting bandwidth and CPU on both client and server.

The WebSocket connection is bidirectional and persistent. Events flow in both directions: user actions from browser to server, and state updates from server to browser. This makes Tunneld's dashboard feel instantaneous even though all logic runs on the server. When a WireGuard handshake completes, every connected dashboard sees the status change within milliseconds.

No JavaScript Duplication

With a JSON API + React frontend, you duplicate logic: validation, business rules, and state management exist in both Elixir and JavaScript. Form validation runs client-side for UX, then server-side for security. State machines are implemented twice. Error handling diverges. The frontend and backend can drift out of sync.

LiveView eliminates this duplication. Validation logic exists once, in Elixir. State machines are implemented once. The HTML is the single source of truth for what the user sees. This halves the code and eliminates an entire class of bugs where frontend and backend disagree about business rules or data shapes.

Simpler Deployment

No separate frontend build, no node_modules, no webpack. Just compile Elixir and deploy. The JavaScript that LiveView needs is small (about 30KB gzipped) and bundled with Phoenix. There is no build step for the frontend beyond asset compilation.

This simplicity matters for Tunneld because it runs on resource-constrained SBCs. A heavy node_modules tree and webpack build would be slow on ARM64. Instead, the release is pure Elixir bytecode plus static assets, and the dashboard loads quickly even on a Raspberry Pi.

Graceful Degradation

LiveView renders real HTML on the initial HTTP request. If JavaScript fails to load or the WebSocket cannot connect, the user still sees the page content. Once the connection establishes, interactivity enables. This progressive enhancement makes the dashboard more resilient than pure SPA approaches that show a blank page without JavaScript.

# Handler:
def handle_event("create_machine", %{"name" => name, "address" => addr}, socket) do
  case Machines.create(%{"name" => name, "address" => addr}) do
    {:ok, machine} -> 
      {:noreply, assign(socket, machines: [machine | socket.assigns.machines])}
    {:error, reason} -> 
      {:noreply, put_flash(socket, :error, reason)}
  end
end

# Or programmatically:
def handle_event("go_setup", _, socket) do
  {:noreply, push_navigate(socket, to: ~p"/setup")}
