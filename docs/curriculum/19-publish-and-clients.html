19 — Publish & Client Access

Key source: lib/tunneld/publish.ex, lib/tunneld/clients.ex

Two Directions Through One Gateway

Everything before this page moves traffic outward: a subnet device reaches the internet, optionally via an exit machine. These two features move traffic inward, and they are deliberately different shapes because they answer different questions.

PublishClient access
Who reaches itanyone on the internetonly people you enrol
ProtocolHTTP/S onlyanything, including UDP
Client softwarenone — a browserthe WireGuard app
Good fora dashboard, a demo, a web appSunshine, SSH, SMB, a media server

A game stream cannot go through Publish: Caddy is an HTTP reverse proxy and Moonlight is latency-sensitive UDP. That is not a gap to be filled later — it is why both exist.

Publish: the Hairpin

A resource already resolves to <name>.tunneld.lan:18000 on the gateway's Caddy. Publishing puts a second Caddy on a managed machine that listens on a public port and reverse-proxies to the gateway's Caddy over the overlay, rewriting the Host header so the gateway's existing route matches. 

internet -> <machine_public_ip>:<port> -> wg -> 10.88.0.1:18000 -> the pool

The choice of upstream is the whole trick. An earlier implementation pointed the remote Caddy straight at the resource's LAN backends — 10.0.0.44:8000 — and could never have worked: the gateway's FORWARD chain is DROP and only permits RELATED,ESTABLISHED back from the overlay, so a connection opened into the LAN dies there.

Proxying at 10.88.0.1:18000 instead means traffic terminates on the gateway (the INPUT chain, where tcp/18000 is already open on every interface) and the gateway then opens its own connection to the backend (OUTPUT). It never touches FORWARD. Publishing therefore needs no new gateway firewall rules and exposes no LAN device to the machine.

Config the machine actually runs

%{
  "admin" => %{"disabled" => true},
  "apps" => %{"http" => %{"servers" => %{
    "pub_<resource_id>" => %{
      "listen" => [":8001"],
      "automatic_https" => %{"disable" => true},
      "routes" => [%{"handle" => [%{
        "handler" => "reverse_proxy",
        "upstreams" => [%{"dial" => "10.88.0.1:18000"}],
        "headers" => %{"request" => %{"set" => %{"Host" => ["printer.tunneld.lan"]}}}
      }]}]
    }
  }}}
}

The admin API is disabled rather than bound to the overlay. A remote admin endpoint is remote config execution, and the previous attempt shipped a bug that pushed admin: 127.0.0.1:2019 to the machine, which would have moved its admin listener and locked the gateway out of every later push. Config is written to /etc/tunneld-caddy.json and loaded by a systemd unit instead.

Client Access: the Gateway Terminates, the Machine Is a Door

A client is a person's device. It gets its own keypair and an address in 10.88.1.0/24, and it always terminates on the gateway: 

at home   client -> 10.0.0.1:51822                            (one hop, no VPS)
away      client -> <machine>:51822 -DNAT-> 10.88.0.1:51822   (machine is a door)

The obvious design — clients peering with the VPS — was rejected. If the machine terminates the session it needs key material, a second WireGuard instance, and its own peer list, and swapping to a closer machine means reissuing every config. Forwarding a port into the tunnel the machine already holds costs two iptables rules and keeps one identity per client everywhere. Same keypair, same address, same peer; only Endpoint differs.

The rule that is not optional

iptables -t nat -A PREROUTING  -p udp --dport 51822 -j DNAT --to-destination 10.88.0.1:51822
iptables -t nat -A POSTROUTING -d 10.88.0.1 -p udp --dport 51822 -j MASQUERADE

With DNAT alone the gateway sees the client's real public address and replies directly out its own uplink. The client then receives an answer from an address it never wrote to, and its NAT drops it — a tunnel that looks correct at both ends and never completes a handshake. The masquerade makes the gateway answer the machine, which un-NATs and returns it down the path the client actually used.

AllowedIPs Is Routing, Not Permission

This distinction caused two separate bugs and is worth internalising.

AllowedIPs in a client's config tells that client what to send down the tunnel. The client owns the file and can set it to 0.0.0.0/0 whenever it likes. It is not a boundary.

The first implementation scoped AllowedIPs per grant — add access to 10.0.0.52, add 10.0.0.52/32 to the config. It failed twice over. It was not a boundary, and because the config is baked in at the moment it is issued, granting access later could not reach a phone that had already scanned the QR: the gateway permitted traffic the phone had no route for.

The config now always routes the whole LAN, and permission lives on the gateway: 

# in the client's config — routing only
AllowedIPs = 10.88.0.0/24, 10.88.1.0/24, 10.0.0.0/24

# on the gateway — the actual boundary, per client, per host
iptables -I FORWARD -i wg-clients -o eth1 -s 10.88.1.2 -d 10.0.0.52 -j ACCEPT

Grants now take effect immediately, with no reissuing and no rescanning.

The DNS Trap

A DNS = line in a WireGuard config is not a hint — the mobile apps apply it as the device's system resolver for as long as the tunnel is up. Naming a resolver the client cannot reach takes the whole phone offline the moment it connects, and it presents as "the VPN broke my internet" rather than as a DNS fault.

Two versions were wrong before the line was removed. DNS = 10.0.0.1 pointed at an address that was not in AllowedIPs, so queries were never routed down the tunnel. DNS = 10.88.1.1 was routable but dnsmasq here runs with interface=eth1 and ignores queries arriving on the client interface. The cost of omitting it is that *.tunneld.lan names do not resolve for clients; the benefit is a phone that still works.

Verifying a UDP Path

A TCP port can be tested with a connect. UDP cannot, which is how a blocked provider firewall stays invisible until someone tries to use the feature. The technique that works is to watch the far end while generating traffic: 

# on the machine
tcpdump -ni any 'udp port 51822'

# from anywhere on the internet
printf probe | nc -u -w1 <machine_ip> 51822

0 packets captured proves the packets never arrive — the provider firewall, not the host. Packets arriving with the source rewritten to the machine's overlay address prove DNAT and SNAT are both working. This diagnosed a blocked UDP/51821 rule and, later, confirmed the client door end to end.

The counterpart on the gateway is wg show: non-zero sent with 0 B received and no latest handshake line means handshakes are leaving and nothing is coming back — blocked upstream, every time.

What This Chapter Actually Teaches

  • Terminating a tunnel where the state already lives beats terminating it where the public IP is — the machine stays disposable.
  • INPUT and FORWARD are different security surfaces; a hairpin through a local proxy can avoid opening the second one entirely.
  • DNAT without SNAT produces asymmetric return paths that look like a working config.
  • Anything a client holds is configuration, not enforcement.
  • A green badge that has not been measured is worse than no badge; publish deliberately shows no health indicator because the provider firewall is invisible from here.
