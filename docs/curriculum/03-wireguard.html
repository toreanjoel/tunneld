03 — WireGuard

Key source: lib/tunneld/overlay.ex

What WireGuard Is

WireGuard is a modern VPN protocol that creates encrypted point-to-point tunnels between machines. Unlike older VPNs (OpenVPN, IPsec), WireGuard is simple: about 4,000 lines of code, built into the Linux kernel since 5.6, and uses only modern cryptography (Curve25519, ChaCha20, BLAKE2s). It is fast, secure, and easy to configure.

Each WireGuard interface is a virtual network device (like wg0 or wg-abc123) that encrypts packets before sending them over UDP to a peer. The peer decrypts them and processes them as if they arrived on a local network. From the application's perspective, the peer appears to be on the same LAN — traffic just happens to be encrypted and tunneled.

WireGuard is not a traditional VPN with a "server" and "clients." It is peer-to-peer: both sides have keypairs, both sides can initiate connections, and the configuration is symmetric. A peer is defined by its public key and allowed IP ranges. This model is called "cryptokey routing."

How WireGuard Works

Cryptokey Routing

The fundamental concept is AllowedIPs: for each peer, you specify which IP addresses (or subnets) should be routed through that peer. When you send a packet to one of those IPs, WireGuard encrypts it with the peer's public key and sends it. When a packet arrives from a peer, WireGuard decrypts it and checks that the source IP is in that peer's AllowedIPs — otherwise, it is dropped. 

# Example WireGuard config (peer section):
[Peer]
PublicKey = AbC123...xyz=
AllowedIPs = 10.88.0.5/32, 10.0.0.0/24
Endpoint = 45.76.183.185:51821
PersistentKeepalive = 25

# This says: "Packets destined for 10.88.0.5 or 10.0.0.0/24 should go
# through this peer. The peer lives at 45.76.183.185:51821."

Keypairs and Identity

Each WireGuard interface has a private/public keypair. The private key is a random 32-byte value; the public key is derived from it via Curve25519. The public key is the identity — peers recognize each other by their public keys, not by IP addresses. 

# Generate a keypair:
$ wg genkey | tee privatekey | wg pubkey > publickey
$ cat privatekey
oNVOqDlRjmqA8bJ5+...=
$ cat publickey
AbC123...xyz=

# The private key never leaves the machine
# The public key is shared with peers

Handshake

When two peers first communicate, they perform a cryptographic handshake to establish a session. The handshake uses Noise IK (initiator knows responder's public key). After the handshake, both sides have symmetric session keys for encrypting data. The session re-keys every 2 minutes or 2^64 messages.

The handshake is initiated by whichever side sends data first. If both sides are behind NAT, neither can reach the other directly. PersistentKeepalive solves this: the configured side sends a keepalive packet every N seconds, which initiates/maintains the handshake and keeps NAT mappings alive. 

# Check handshake status:
$ wg show wg-d4f4632f
interface: wg-d4f4632f
  public key: AbC123...xyz=
  private key: (hidden)
  listening port: 51821

peer: DEF456...=
  endpoint: 45.76.183.185:51821
  allowed ips: 0.0.0.0/0
  latest handshake: 47 seconds ago   # <-- handshake is working
  transfer: 1.23 MiB received, 456 KiB sent
  persistent keepalive: every 25 seconds

Table=off and Manual Routing

By default, wg-quick (the WireGuard helper) automatically adds routes for AllowedIPs to the main routing table. This is convenient for simple setups but problematic when you have multiple peers with overlapping AllowedIPs (e.g., both allowing 0.0.0.0/0).

Table = off tells wg-quick not to modify the routing table at all. You then add routes manually with PostUp commands or ip route. This is what Tunneld uses because it needs fine-grained control over per-device egress routing. 

# WireGuard config with Table=off:
[Interface]
Address = 10.88.0.1/32
PrivateKey = oNVOqDlRjmqA8bJ5+...=
Table = off
PostUp = ip route add 10.88.0.5/32 dev wg-d4f4632f

[Peer]
PublicKey = DEF456...=
AllowedIPs = 0.0.0.0/0
Endpoint = 45.76.183.185:51821
PersistentKeepalive = 25

How Tunneld Uses WireGuard

Tunneld uses WireGuard to make remote machines appear local. The implementation is in lib/tunneld/overlay.ex. Here is the design:

One Interface Per Machine

Each enrolled remote machine gets its own WireGuard interface on the gateway, named wg-<short_hash> (the first 8 characters of a SHA256 hash of the machine ID). This keeps interface names under the 15-character limit imposed by Linux. 

# From lib/tunneld/overlay.ex:
def iface_name(id) do
  short = :crypto.hash(:sha256, id) |> Base.encode16(case: :lower) |> String.slice(0, 8)
  "wg-#{short}"  # e.g., "wg-d4f4632f"
end

Gateway Dials Out

The gateway often moves and sits behind NAT (home internet, mobile hotspot). Remote VMs have stable public IPs. So the gateway is the initiator: it sets PersistentKeepalive = 25 and Endpoint points to the VM's public IP. 

# Gateway-side config (generated in overlay.ex):
[Interface]
Address = 10.88.0.1/32
PrivateKey = (gateway's private key)
Table = off
PostUp = ip route add 10.88.0.5/32 dev wg-d4f4632f

[Peer]
PublicKey = (target machine's public key)
AllowedIPs = 0.0.0.0/0
Endpoint = 45.76.183.185:51821
PersistentKeepalive = 25

Key Generation and Exchange

The keypair for a machine is generated on the gateway. The gateway's keypair for this tunnel is stored under TUNNELD_DATA/wg/<machine_id>. A separate keypair is generated for the target and pushed over SSH. 

# From lib/tunneld/overlay.ex (simplified):
defp exchange_keys(machine) do
  # Generate gateway keypair if not exists
  {gw_pub, gw_priv} = gen_keypair()
  File.write!(priv_path, gw_priv)
  File.chmod!(priv_path, 0o600)

  # Generate target keypair
  {t_pub, t_priv} = gen_keypair()

  # Build target config
  target_conf = """
  [Interface]
  Address = #{overlay_ip}/32
  PrivateKey = #{t_priv}
  Table = off
  ...
  """

  # Push to target via SSH
  write_remote(machine, "/etc/wireguard/#{iface}.conf", target_conf)

  {:ok, t_pub}
end

The ensure_peer Function

The main entry point is ensure_peer/1, which is idempotent: calling it multiple times converges to the same state. 

# From lib/tunneld/overlay.ex:
def ensure_peer(machine) do
  if @mock do
    {:ok, %{overlay_ip: mock_overlay_ip(machine)}}
  else
    real_ensure_peer(machine)
  end
end

defp real_ensure_peer(machine) do
  iface = iface_name(machine["id"])
  with {:ok, target_pub} <- exchange_keys(machine),
       :ok <- install_target(machine, target_pub, iface),
       {:ok, _} <- configure_gateway(machine, target_pub, iface) do
    {:ok, %{overlay_ip: overlay_ip_for(machine)}}
  end
end

Why WireGuard

Why Not SSH Tunnels

The previous architecture used ssh -L (local port forwards) to reach remote services. This had severe problems: tunnel processes leaked on restart (ssh -f daemonizes), port conflicts happened, and the code had to branch everywhere on location. WireGuard replaces all of it with a kernel-level, persistent, encrypted tunnel.

Why Table=off

Without Table = off, wg-quick would add a default route through each peer's interface. With multiple peers (each allowing 0.0.0.0/0 for egress purposes), routes would conflict. Table = off lets Tunneld use policy routing (see the Egress chapter) to route different devices through different peers.

Why PersistentKeepalive = 25

NAT mappings expire after a period of inactivity. 25 seconds is conservative — most NAT devices keep mappings for 30-60 seconds. Keepalives also ensure the handshake happens promptly when the gateway restarts.

Examples

View WireGuard status

# On the gateway:
$ wg show
interface: wg-d4f4632f
  public key: AbC123...xyz=
  listening port: 51821

peer: DEF456...=
  endpoint: 45.76.183.185:51821
  allowed ips: 0.0.0.0/0
  latest handshake: 12 seconds ago
  transfer: 5.67 MiB received, 1.23 MiB sent
  persistent keepalive: every 25 seconds

Bring up a WireGuard interface manually

# On any machine with wireguard-tools installed:
$ wg-quick up wg-d4f4632f
[#] ip link add wg-d4f4632f type wireguard
[#] wg setconf wg-d4f4632f /dev/fd/63
[#] ip -4 address add 10.88.0.1/32 dev wg-d4f4632f
[#] ip link set mtu 1420 up dev wg-d4f4632f

# With Table=off, no routes are added automatically

Generate a WireGuard keypair

# Generate private key, derive public key:
$ wg genkey | tee /etc/wireguard/privatekey | wg pubkey > /etc/wireguard/publickey
$ chmod 600 /etc/wireguard/privatekey

# View the keys:
$ cat /etc/wireguard/privatekey
oNVOqDlRjmqA8bJ5+...=
$ cat /etc/wireguard/publickey
AbC123...xyz=

Add a manual route for a peer

# After bringing up the interface with Table=off:
$ ip route add 10.88.0.5/32 dev wg-d4f4632f

# Verify:
$ ip route show | grep 10.88.0.5
10.88.0.5 dev wg-d4f4632f scope link
