05 — Routing Tables & Egress

Key source: lib/tunneld/egress.ex, lib/tunneld/overlay.ex

What Policy Routing Is

Standard routing decides where to send a packet based only on its destination address. Policy routing extends this: you can route based on source address, incoming interface, packet marking, or other criteria. This enables per-device or per-application routing decisions — essential for Tunneld's egress feature where different devices on the same subnet can exit through different remote machines.

Linux supports multiple routing tables. The default table (ID 254, called "main") is what ip route show displays. You can create additional tables (IDs 1-252) and define rules (ip rule) that select which table to use for which packets. This is called RPDB — the Routing Policy Database.

Tunneld uses policy routing to implement "exit nodes": a device on the LAN can have its traffic routed through a remote VPS instead of the gateway's own upstream. Each exit machine gets its own routing table with a default route through its WireGuard tunnel, and ip rule entries steer specific devices' traffic to that table.

How Policy Routing Works

The Rule Lookup Process

When the kernel needs to route a packet, it walks through the RPDB in priority order. Each rule has a selector (what packets match) and an action (usually "lookup table N"). The first matching rule wins. 

# View the routing policy database:
$ ip rule show
0:      from all lookup local       # First: check local addresses
32766:  from all lookup main        # Then: check main routing table
32767:  from all lookup default     # Finally: check default table

# Rules are processed in priority order (lower number = higher priority)

Multiple Routing Tables

Each routing table is independent. You can have a different default gateway in each table. This is how Tunneld routes one device through a VPS while another uses the normal upstream. 

# The main table (254):
$ ip route show table main
default via 192.168.1.1 dev eth0   # Normal internet exit
10.0.0.0/24 dev eth1 scope link    # Local subnet

# A custom table (100) for an exit node:
$ ip route show table 100
default dev wg-d4f4632f scope link # Exit via WireGuard tunnel
10.0.0.0/24 dev eth1 scope link    # Keep local traffic local

Source-Based Rules

The from selector matches the source IP of packets. By adding a rule from 10.0.0.50 lookup 100, all packets from device 10.0.0.50 will use table 100 (the exit node's table) instead of the main table. 

# Add a source-based rule:
$ ip rule add from 10.0.0.50 lookup 100

# View the result:
$ ip rule show
0:      from all lookup local
32765:  from 10.0.0.50 lookup 100   # <-- New rule
32766:  from all lookup main
32767:  from all lookup default

# Now 10.0.0.50's traffic uses table 100's default route
# (the WireGuard tunnel) instead of the normal exit

DNS Leaks

A subtle problem: even if a device's traffic exits through a VPS, its DNS queries may still go to the gateway's upstream DNS. This "leaks" the user's browsing patterns to the local ISP. Tunneld surfaces this as an explicit choice in the UI rather than silently deciding.

How Tunneld Uses Egress

The egress implementation is in lib/tunneld/egress.ex. The core flow is: (1) allocate a routing table for the exit machine, (2) add a default route through its WireGuard interface, (3) add ip rule entries for each device that should use it.

Table Allocation

Each exit machine gets a stable routing table ID (100+). IDs are persisted in egress_tables.json so they survive restarts. This is important because ip rule entries reference table IDs by number. 

# From lib/tunneld/egress.ex:
@table_base 100

def table_for(machine) do
  tables = read_tables()  # From egress_tables.json
  id = machine["id"]

  case Map.get(tables, id) do
    nil ->
      n = allocate_table(tables)  # Find unused ID >= 100
      write_tables(Map.put(tables, id, n))
      n
    n ->
      n
  end
end

The route_device Function

This is the main entry point for routing a device through an exit: 

# From lib/tunneld/egress.ex (simplified):
def route_device(machine, device_ip, opts \\ []) do
  dns = Keyword.get(opts, :dns, "local")

  if @mock do
    {:ok, %{device_ip: device_ip, machine: machine["id"], table: table_for(machine)}}
  else
    real_route_device(machine, device_ip, dns)
  end
end

defp real_route_device(machine, device_ip, dns) do
  id = machine["id"]
  iface = Overlay.iface_name(id)    # e.g., "wg-d4f4632f"
  table = table_for(machine)        # e.g., "100"
  overlay_ip = Overlay.address_for(machine)

  with :ok <- assert_gateway_role(device_ip),
       {:ok, _} <- add_rule(device_ip, table),
       {:ok, _} <- add_default_route(overlay_ip, iface, table),
       {:ok, _} <- add_lan_route(table),
       :ok <- add_forward_rules(iface),
       {:ok, _} <- add_vm_device_route(machine, device_ip, iface),
       :ok <- maybe_set_dns(device_ip, machine, dns) do
    {:ok, %{device_ip: device_ip, machine: id, table: table, dns: dns}}
  end
end

Case Study: The with-chain Bug

The original code had a subtle bug: the with chain expected :ok from each step, but add_rule/2 and others returned {:ok, output}. The pattern mismatch caused the chain to short-circuit after the first step, never adding routes. This was found in production when devices lost internet after selecting an exit.

The fix: change patterns from :ok <- add_rule(...) to {:ok, _} <- add_rule(...). See lib/TODO.md section 11 for the full investigation.

Gateway Role Assertion

Egress only works if Tunneld is actually the device's default gateway. If a device has a static route that bypasses the gateway, egress silently does nothing. assert_gateway_role/1 checks this: 

# From lib/tunneld/egress.ex:
defp assert_gateway_role(device_ip) do
  gateway = gateway_ip()

  case run_gateway("ip route get #{device_ip} 2>/dev/null") do
    {:ok, out} ->
      if String.contains?(out, gateway) do
        :ok
      else
        {:error, :device_not_through_gateway}
      end
    _ ->
      {:error, :cannot_verify_device_path}
  end
end

Why Policy Routing

Why Not VRFs

Linux VRFs (Virtual Routing and Forwarding) are another approach to multi-table routing, used in network equipment. They are more complex to set up and less portable across kernel versions. Policy routing with ip rule is simpler and sufficient for Tunneld's use case.

Why Per-Machine Tables

Each exit machine gets its own table so that multiple devices can use different exits simultaneously. If all exits shared one table, you could only have one active exit at a time.

Why Persist Table IDs

Table IDs could be computed (e.g., hash the machine ID). But persisting them in egress_tables.json ensures stability: if you restart Tunneld, the same machine gets the same table ID, matching any ip rule entries that might not have been cleaned up.

Examples

Set up egress manually

# 1. Create routing table 100 with a default route through wg-d4f4632f:
$ ip route add default dev wg-d4f4632f table 100

# 2. Keep local traffic local:
$ ip route add 10.0.0.0/24 dev eth1 table 100

# 3. Route device 10.0.0.50 through table 100:
$ ip rule add from 10.0.0.50 lookup 100

# 4. Verify:
$ ip route get 8.8.8.8 from 10.0.0.50
8.8.8.8 from 10.0.0.50 dev wg-d4f4632f table 100 ...

Remove egress for a device

# Remove the ip rule:
$ ip rule del from 10.0.0.50 lookup 100

# Verify it's gone:
$ ip rule show | grep 10.0.0.50
(no output)

# The device now uses the main table (normal exit)

Debug routing decisions

# See which table a packet would use:
$ ip route get 8.8.8.8 from 10.0.0.50
8.8.8.8 from 10.0.0.50 via 10.88.0.5 dev wg-d4f4632f table 100 src 10.0.0.1

# List all rules:
$ ip rule show
0:      from all lookup local
32765:  from 10.0.0.50 lookup 100
32766:  from all lookup main

# Show a specific table:
$ ip route show table 100

Check the VM has return routes

# On the exit VM, verify it knows how to reach the device:
$ ip route show | grep 10.0.0.50
10.0.0.50 dev wg-d4f4632f scope link

# This route is added by add_vm_device_route() in egress.ex
