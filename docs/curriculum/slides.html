00 — Orientation

What Tunneld Is

Tunneld is software for a dual-NIC ARM64 single-board computer that turns it into a wired edge gateway for a private subnet. Think of it as a dedicated appliance that sits between your internet connection and your local devices, giving you complete control over how traffic flows, what services are exposed, and how remote machines integrate into your local network.

The gateway has two ethernet interfaces: one connects to the internet (the "upstream"), and one connects to your local network (the "downstream"). Devices plugged into the downstream port receive IP addresses automatically via DHCP, can resolve names via DNS, and get internet access through the gateway's NAT. The gateway runs a web dashboard where you manage everything.

00 — Orientation

What Tunneld Is (cont.)

But Tunneld does more than just route packets. It discovers what services are running on any Linux machine you give it SSH access to, and lets you expose those services either locally on your subnet or publicly on the internet. Remote VPS servers appear as if they were on your local network, thanks to WireGuard tunnels. This is managed through a real-time LiveView dashboard — no CLI memorization required for day-to-day operations.

00 — Orientation

The Problem It Solves

Most home and small-office networks have a consumer router as the gateway. That router does DHCP, DNS, NAT, and maybe some basic port forwarding — but it is a black box. You cannot run arbitrary software on it, you cannot script it, and you cannot integrate it with your own tools. If you want to expose a service running on a Raspberry Pi in your closet, you need to figure out port forwarding, dynamic DNS, maybe a reverse proxy, and hope your ISP does not block the ports.

Tunneld replaces that black box with a programmable gateway you control. It is not a router firmware replacement — it is a dedicated machine that takes over the gateway role for a specific subnet. Your existing router can stay upstream providing internet; Tunneld just becomes the gateway for your private network.

00 — Orientation

The Problem It Solves (cont.)

The harder problem is fleet management. You might have a NAS in your closet, a GPU server under your desk, a VPS in the cloud, and a Raspberry Pi running Home Assistant. Each has services you want to access, each has its own IP or hostname, and keeping track of what is running where is a spreadsheet nightmare. Tunneld gives them all names on one domain (*.tunneld.lan), load-balances across backends, and shows you what is listening in one dashboard.

00 — Orientation

The Two Big Ideas · 1. A Resource Is an Address, Not a Container

Early versions of Tunneld were tightly coupled to Incus (an LXD fork). You could only expose services running in Incus containers. That coupling was wrong because it answered the wrong question.

The old question: "What containers are running on this machine?"
The right question: "What is listening on this machine?"

A single SSH command — ss -tlnp — enumerates every listening TCP socket on any Linux host, regardless of whether it is a Docker container, an Incus container, a systemd service, a Go binary running in tmux, or something that does not exist yet. Tunneld asks that question, shows you the list, and lets you pick one. That listener becomes a resource.

00 — Orientation

The Two Big Ideas · 1. A Resource Is an Address, Not a Container (cont.)

This is implemented in lib/tunneld/machines/runtime.ex. The listeners/1 function runs ss -tlnp over SSH, parses the output, and returns a list of maps with address, port, process name, and optionally which container owns it (if a container runtime is detected). But discovery is never gated on a runtime being present — a bare box with a systemd service works identically.

$ ss -tlnp

LISTEN   0      244    127.0.0.1:5432       0.0.0.0:*         users:(("postgres",pid=5678,fd=5))

The Two Big Ideas · 1. A Resource Is an Address, Not a Container (cont.)

Tunneld parses this into structured data. The nginx process listening on port 80 can become a resource named web.tunneld.lan. The postgres process stays internal because it binds only to localhost. The operator sees both and decides what to expose.

00 — Orientation

The Two Big Ideas · 2. WireGuard Makes Remote Machines Local

The old architecture had a sharp fork: local machines (on the same subnet as the gateway) were reachable directly, but remote machines (VPS servers) required SSH tunnels. The SSH tunnel approach was fragile — tunnels leaked on restart, port conflicts happened, and the code had to branch everywhere on location.

The new architecture collapses that fork. Every enrolled machine becomes a WireGuard peer of the gateway. Remote machines get an overlay IP (from the 10.88.0.0/24 subnet by default). Once a machine is a peer, Tunneld can route to it directly — no SSH tunnels, no special cases.

00 — Orientation

The Two Big Ideas · 2. WireGuard Makes Remote Machines Local (cont.)

This is implemented in lib/tunneld/overlay.ex. The key function is address_for/1: given a machine, it returns either its LAN IP (if the machine is on the gateway's subnet) or its overlay IP (if remote). The rest of the codebase just calls address_for/1 and does not care about location. 

# In lib/tunneld/overlay.ex:
def address_for(machine) do
  if same_subnet?(machine["address"]) do
    machine["address"]         # e.g., 10.0.0.50
  else
    overlay_ip_for(machine)    # e.g., 10.88.0.5
  end
end

The gateway dials out to each machine (because the gateway often moves and sits behind NAT, while VMs have stable public IPs). PersistentKeepalive=25 keeps the tunnel alive. Once the WireGuard interface is up, services on that machine are as reachable as services on a local Raspberry Pi.

00 — Orientation

Why This Architecture

The two big ideas have consequences that simplify the entire codebase:

00 — Orientation

Why This Architecture (cont.)

  • No container CRUD. Tunneld never creates, starts, or stops containers. It discovers what is already running. If you want to run an Ollama container, you SSH into your machine and run it yourself. Tunneld then sees it listening on port 11434 and lets you expose it. This means Tunneld does not need to understand Docker compose files, Incus profiles, or Kubernetes manifests — it only needs to understand listening sockets.
  • No SSH tunnels. The old Expose module used ssh -L to create local port forwards for remote services. These tunnels leaked processes on restart, conflicted on port numbers, and added fragile state. WireGuard replaces all of it with one persistent, encrypted, kernel-level tunnel per machine.
  • Exactly one thing installed on targets. Tunneld installs WireGuard (wireguard-tools) on managed machines. That is it. If something else is needed (Docker, Incus, Node.js, whatever), the operator installs it. Tunneld just discovers the result.
  • Reconciliation over repair. Because remote state is authoritative (a machine knows what it is running better than Tunneld's cached state), there is one function — Tunneld.Reconcile.reconcile/1 — that checks live state and diffs against desired. No bespoke "reopen on boot" logic.

00 — Orientation

Mental Model Example

Here is a concrete example. You have three machines:

  1. A NUC on your desk running Ollama (10.0.0.50, local)
  2. A Raspberry Pi in the closet running Pi-hole (10.0.0.51, local)
  3. A Vultr VPS running a web app (45.76.183.185, remote)

You enroll all three in Tunneld. The local machines are reachable at their LAN IPs. The VPS becomes a WireGuard peer and gets overlay IP 10.88.0.2. Now you can: 

# From any device on the subnet:
curl http://ollama.tunneld.lan:18000/api/generate   # -> 10.0.0.50:11434
curl http://pihole.tunneld.lan:18000                # -> 10.0.0.51:80
curl http://webapp.tunneld.lan:18000                # -> 10.88.0.2:3000 (over WireGuard)

00 — Orientation

Mental Model Example (cont.)

All three are just "resources" — the fact that one is remote is an implementation detail. The address_for/1 function returns the right IP, Caddy proxies to it, and the WireGuard kernel module handles the encryption transparently.

If the VPS goes down, the resource health check fails and the dashboard shows it red. If you want to fail over to a local backup, you add both backends to the resource pool and Caddy load-balances across whichever is healthy.

01 — Architecture

What the Architecture Is

Tunneld is an Elixir/Phoenix application that orchestrates several external services to provide gateway functionality. It is not a monolith that does everything itself — it drives dnsmasq for DHCP/DNS, Caddy for reverse proxying, iptables for firewalling and NAT, and WireGuard for encrypted tunnels. The Elixir application is the control plane that coordinates these components and presents a unified interface via the LiveView dashboard.

The application runs on the BEAM virtual machine, which provides lightweight processes, supervision trees for fault tolerance, and hot code reloading. Phoenix provides the web framework, and LiveView enables real-time updates without writing JavaScript. State is persisted to JSON files on disk (no database), and PubSub broadcasts changes to connected dashboards.

Let us trace what happens when you click "Make Exit Node" for a machine in the dashboard:

Request Lifecycle (cont.)

  1. Browser → Phoenix Endpoint
    The dashboard is a LiveView mounted at /. When you click the button, the browser sends a message over the existing WebSocket connection. Phoenix routes it to the handle_event("make_exit_node", %{"id" => id}, socket) callback in dashboard.ex.
  2. LiveView → Egress Module
    The handler calls Tunneld.Egress.ensure_exit_capable(machine). This is a plain Elixir module, not a GenServer — it runs in the LiveView process.
  3. Egress → SSH
    ensure_exit_capable/1 needs to run commands on the machine. It calls Tunneld.Machines.SSH.run(machine, "sysctl -w net.ipv4.ip_forward=1 ..."). SSH uses System.cmd/3 to shell out to the ssh binary.
  4. SSH → Target Machine
    The SSH command runs on the target, enabling IP forwarding and adding iptables rules. Output is captured and returned to Elixir as {:ok, output}.
  5. Egress → Persistence
    If successful, egress.ex allocates a routing table ID for this machine and writes it to egress_tables.json via Tunneld.Persistence.
  6. Machines → PubSub
    Tunneld.Machines.broadcast/2 publishes on the "component:machines" topic. The payload is a map: %{id: "machines", event: :updated, data: machine}.
  7. PubSub → All Dashboards
    Every connected dashboard is subscribed to that topic. Their handle_info(%{id: "machines"} = msg, socket) callback receives the update and re-renders the machine list.
  8. LiveView → Browser
    Phoenix calculates the diff between the old and new HTML, serializes it, and sends it over the WebSocket. The browser's LiveView JS library patches the DOM. The machine now shows "Exit Node: Yes".

01 — Architecture

Why This Design · Plain Modules Over GenServers

Many modules that look like they might need a GenServer are actually plain modules: Overlay, Egress, Caddy, Reconcile, Iptables. This is deliberate.

A GenServer is appropriate when you need to hold mutable state across calls or serialize access to a shared resource. But Egress.route_device/3 does not need either — it reads from disk, shells out to ip rule, writes to disk, and returns. If two concurrent calls race, they converge to the same state (idempotence). Wrapping this in a GenServer would serialize operations unnecessarily, adding latency.

01 — Architecture

Why This Design · JSON on Disk, No Database

Tunneld does not use PostgreSQL, SQLite, or any database. State is JSON files under /var/lib/tunneld/ (or data/ in dev). This is intentional:

  • A dedicated database adds operational complexity on an SBC with limited resources.
  • The data is small (a few hundred machines at most) and reads are infrequent.
  • Atomic writes with backup (write to temp, rename) are enough for durability.
  • The real source of truth is the remote machines anyway — disk is just a hint.

01 — Architecture

Why This Design · PubSub for Real-Time Updates

When a device gets a DHCP lease, all connected dashboards should see it immediately. This is done via Phoenix PubSub: the Devices server broadcasts on the "component:devices" topic, and every subscribed LiveView receives the update and re-renders.

02 — Networking Foundations

What Networking Is

Networking is how computers find and talk to each other. At its core, every device on a network has an address (like a phone number), and data is broken into packets that travel from source to destination through intermediate devices. The rules for how this works are layered: at the bottom, raw electrical signals; at the top, applications like web browsers.

Tunneld operates primarily at layers 3 and 4 of the OSI model: the network layer (IP addressing, routing) and the transport layer (TCP/UDP, ports). Understanding these layers is essential because Tunneld manipulates IP addresses, routes packets between networks, and exposes services bound to specific ports.

02 — Networking Foundations

What Networking Is (cont.)

The key concepts you need to understand are: IP addresses (how devices are identified), subnets (how addresses are grouped), routing (how packets find their way), NAT (how private addresses reach the public internet), ports (how multiple services share one IP), and sockets (how applications bind to addresses and ports).

02 — Networking Foundations

How Networking Works · IP Addresses

An IPv4 address is a 32-bit number, written as four octets separated by dots: 192.168.1.50. Each octet ranges from 0 to 255. This gives about 4.3 billion possible addresses — not enough for every device, which is why NAT and private addresses exist.

Private address ranges (RFC 1918) are reserved for local networks and are not routable on the public internet:

  • 10.0.0.0/8 — 16 million addresses
  • 172.16.0.0/12 — 1 million addresses
  • 192.168.0.0/16 — 65,536 addresses

Tunneld does not hardcode a LAN subnet: the gateway's own address comes from the GATEWAY environment variable (config/runtime.exs raises in production if it is missing), and the subnet is derived from it. The examples on this page use 10.0.0.0/24 with the gateway at 10.0.0.1. The overlay subnet for WireGuard is 10.88.0.0/24. Both are private ranges.

def network(key) do

How Networking Works · Subnets and CIDR Notation

A subnet is a logical division of an IP network. CIDR notation (10.0.0.0/24) specifies the network prefix length — how many bits identify the network vs. the host. /24 means the first 24 bits are the network portion, leaving 8 bits (256 addresses) for hosts. 

# CIDR examples:
10.0.0.0/24    = 10.0.0.0   to 10.0.0.255   (256 addresses)
10.0.0.0/16    = 10.0.0.0   to 10.0.255.255 (65,536 addresses)
10.88.0.0/24   = 10.88.0.0  to 10.88.0.255  (Tunneld overlay subnet)

# The /24 is called the "subnet mask" or "prefix length"
# In dotted form: /24 = 255.255.255.0

Two devices are on the "same subnet" if their network portions match. In lib/tunneld/overlay.ex, the same_subnet?/1 function checks this by comparing the first three octets (for a /24):

# From lib/tunneld/overlay.ex:
defp same_subnet?(address) do
  gw = Tunneld.Config.gateway_ip()  # e.g., "10.0.0.1"
  with {:ok, a} <- parse_ip4(address),
       {:ok, g} <- parse_ip4(gw) do
    match?({[x, y, z, _], [x, y, z, _]}, {a, g})  # First 3 octets match
  else
    _ -> false
  end
end

02 — Networking Foundations

How Networking Works · Routing

Routing is how packets find their way from source to destination. Every device has a routing table that says "packets for network X go out interface Y (optionally via gateway Z)." When a packet arrives, the kernel consults this table to decide what to do.

The most important route is the default gateway: where to send packets when no more specific route matches. On Tunneld's subnet, every device's default gateway is the Tunneld box itself (10.0.0.1). This is set via DHCP option 3. 

# Viewing the routing table on Linux:
$ ip route show
default via 10.0.0.1 dev eth0 proto dhcp metric 100
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.50
10.88.0.0/24 dev wg-d4f4632f proto kernel scope link

# Reading: "default" = any destination not matched below
# "via 10.0.0.1" = send to the gateway
# "dev eth0" = out this interface

02 — Networking Foundations

How Networking Works · NAT (Network Address Translation)

NAT allows devices on a private subnet to reach the public internet using the gateway's public IP. The gateway rewrites the source IP of outgoing packets (from the private address to its own public address) and remembers the mapping so replies can be routed back to the right device.

Tunneld uses MASQUERADE, a form of SNAT (source NAT) that automatically uses the outgoing interface's address. This is configured in lib/tunneld/iptables.ex: 

# From lib/tunneld/iptables.ex:
defp internet_passthrough() do
  System.cmd("iptables", [
    "-t", "nat",              # Use the NAT table
    "-A", "POSTROUTING",      # After routing decision, before leaving
    "-o", get_env(:upstream), # On packets going out the upstream interface
    "-j", "MASQUERADE"        # Rewrite source IP to the interface's IP
  ])
end

03 — WireGuard

What WireGuard Is

WireGuard is a modern VPN protocol that creates encrypted point-to-point tunnels between machines. Unlike older VPNs (OpenVPN, IPsec), WireGuard is simple: about 4,000 lines of code, built into the Linux kernel since 5.6, and uses only modern cryptography (Curve25519, ChaCha20, BLAKE2s). It is fast, secure, and easy to configure.

Each WireGuard interface is a virtual network device (like wg0 or wg-abc123) that encrypts packets before sending them over UDP to a peer. The peer decrypts them and processes them as if they arrived on a local network. From the application's perspective, the peer appears to be on the same LAN — traffic just happens to be encrypted and tunneled.

03 — WireGuard

What WireGuard Is (cont.)

WireGuard is not a traditional VPN with a "server" and "clients." It is peer-to-peer: both sides have keypairs, both sides can initiate connections, and the configuration is symmetric. A peer is defined by its public key and allowed IP ranges. This model is called "cryptokey routing."

03 — WireGuard

How WireGuard Works · Cryptokey Routing

The fundamental concept is AllowedIPs: for each peer, you specify which IP addresses (or subnets) should be routed through that peer. When you send a packet to one of those IPs, WireGuard encrypts it with the peer's public key and sends it. When a packet arrives from a peer, WireGuard decrypts it and checks that the source IP is in that peer's AllowedIPs — otherwise, it is dropped. 

# Example WireGuard config (peer section):
[Peer]
PublicKey = AbC123...xyz=
AllowedIPs = 10.88.0.5/32, 10.0.0.0/24
Endpoint = 45.76.183.185:51821
PersistentKeepalive = 25

# This says: "Packets destined for 10.88.0.5 or 10.0.0.0/24 should go
# through this peer. The peer lives at 45.76.183.185:51821."

03 — WireGuard

How WireGuard Works · Keypairs and Identity

Each WireGuard interface has a private/public keypair. The private key is a random 32-byte value; the public key is derived from it via Curve25519. The public key is the identity — peers recognize each other by their public keys, not by IP addresses. 

# Generate a keypair:
$ wg genkey | tee privatekey | wg pubkey > publickey
$ cat privatekey
oNVOqDlRjmqA8bJ5+...=
$ cat publickey
AbC123...xyz=

# The private key never leaves the machine
# The public key is shared with peers

03 — WireGuard

How WireGuard Works · Handshake

When two peers first communicate, they perform a cryptographic handshake to establish a session. The handshake uses Noise IK (initiator knows responder's public key). After the handshake, both sides have symmetric session keys for encrypting data. The session re-keys every 2 minutes or 2^64 messages.

The handshake is initiated by whichever side sends data first. If both sides are behind NAT, neither can reach the other directly. PersistentKeepalive solves this: the configured side sends a keepalive packet every N seconds, which initiates/maintains the handshake and keeps NAT mappings alive.

03 — WireGuard

Why WireGuard · Why Not SSH Tunnels

The previous architecture used ssh -L (local port forwards) to reach remote services. This had severe problems: tunnel processes leaked on restart (ssh -f daemonizes), port conflicts happened, and the code had to branch everywhere on location. WireGuard replaces all of it with a kernel-level, persistent, encrypted tunnel.

03 — WireGuard

Why WireGuard · Why Table=off

Without Table = off, wg-quick would add a default route through each peer's interface. With multiple peers (each allowing 0.0.0.0/0 for egress purposes), routes would conflict. Table = off lets Tunneld use policy routing (see the Egress chapter) to route different devices through different peers.

03 — WireGuard

Why WireGuard · Why PersistentKeepalive = 25

NAT mappings expire after a period of inactivity. 25 seconds is conservative — most NAT devices keep mappings for 30-60 seconds. Keepalives also ensure the handshake happens promptly when the gateway restarts.

04 — iptables & NAT

What iptables Is

iptables is the traditional Linux firewall and packet manipulation tool. It is the userspace interface to Netfilter, the kernel subsystem that intercepts and processes network packets as they flow through the system. Every packet entering, leaving, or being forwarded through a Linux machine passes through Netfilter hooks where iptables rules can match it, log it, modify it, accept it, or drop it.

Despite its name, iptables does much more than filtering. It can rewrite addresses (NAT), mark packets for later processing, redirect traffic to different ports, and track connection state. For Tunneld, iptables is the foundation of internet access (NAT masquerading), DNS interception, and packet forwarding between interfaces.

04 — iptables & NAT

What iptables Is (cont.)

iptables organizes rules into tables, chains, and targets. Understanding this hierarchy is essential because adding a rule in the wrong place does nothing (or worse, breaks connectivity). The most common tables are filter (for accepting/dropping packets), nat (for address translation), and mangle (for packet modification).

04 — iptables & NAT

How iptables Works · Tables and Chains

iptables has four main tables, each with built-in chains that correspond to different points in packet processing:

  • filter (default table): INPUT, FORWARD, OUTPUT — for packet filtering
  • nat: PREROUTING, INPUT, OUTPUT, POSTROUTING — for address translation
  • mangle: all five chains — for packet modification (TTL, TOS, marking)
  • raw: PREROUTING, OUTPUT — for connection tracking exemptions

Packets flow through chains in a specific order depending on their path: 

Incoming packet:
  PREROUTING (nat/mangle) → routing decision
    ↓                              ↓
  INPUT (filter)              FORWARD (filter)
    ↓                              ↓
  local process              POSTROUTING (nat)
                                   ↓
                             outgoing interface

Locally generated packet:
  OUTPUT (nat/filter/mangle) → POSTROUTING (nat) → outgoing interface

04 — iptables & NAT

How iptables Works · Targets

When a rule matches, its target determines what happens:

  • ACCEPT — allow the packet, stop processing this chain
  • DROP — silently discard the packet
  • REJECT — discard and send an error reply (ICMP or TCP RST)
  • MASQUERADE — rewrite source IP to the outgoing interface's IP (SNAT variant)
  • REDIRECT — redirect to a local port (for transparent proxying)
  • RETURN — return to the calling chain
  • LOG — log to syslog, continue processing
# Example rules:
iptables -A INPUT -p tcp --dport 22 -j ACCEPT    # Accept SSH
iptables -A INPUT -j DROP                         # Drop everything else

iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE  # NAT on eth0

04 — iptables & NAT

How iptables Works · Connection Tracking (conntrack)

Netfilter tracks the state of connections. This is essential for stateful firewalling: you can accept incoming packets that are part of an established connection without opening ports permanently.

Connection states:

  • NEW — first packet of a new connection
  • ESTABLISHED — part of an existing connection
  • RELATED — related to an existing connection (e.g., ICMP error)
  • INVALID — packet doesn't match any known connection
# Accept return traffic for existing connections:
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# This one rule handles all reply packets for connections
# initiated by the local machine

04 — iptables & NAT

How iptables Works · MASQUERADE: Source NAT for Dynamic IPs

NAT masquerading rewrites the source IP of outgoing packets to the outgoing interface's current IP address, and remembers the mapping so replies can be translated back. This is how devices on a private subnet reach the public internet through a gateway. 

# Without NAT:
Device 10.0.0.50 sends packet to 8.8.8.8
Packet has source IP 10.0.0.50 (private, non-routable)
8.8.8.8 cannot reply - doesn't know how to reach 10.0.0.50

# With MASQUERADE:
Device 10.0.0.50 sends packet to 8.8.8.8
Gateway rewrites source IP to 192.168.1.100 (gateway's upstream IP)
8.8.8.8 replies to 192.168.1.100
Gateway looks up conntrack, rewrites dest IP back to 10.0.0.50

# From lib/tunneld/iptables.ex (simplified):
def reset() do
  flush_tables()

  # Start with ACCEPT policies while adding rules
  # (so we don't lock ourselves out mid-configuration)
  System.cmd("iptables", ["-P", "INPUT", "ACCEPT"])
  System.cmd("iptables", ["-P", "FORWARD", "ACCEPT"])

  # Allow loopback
  System.cmd("iptables", ["-A", "INPUT", "-i", "lo", "-j", "ACCEPT"])

  # Allow established connections
  System.cmd("iptables", ["-A", "INPUT", "-m", "conntrack", 
    "--ctstate", "ESTABLISHED,RELATED", "-j", "ACCEPT"])

  # Allow specific ports (SSH, HTTP, Caddy's resource port)
  for port <- [80, 22, Tunneld.Caddy.public_port()] do
    System.cmd("iptables", ["-A", "INPUT", "-p", "tcp", 
      "--dport", to_string(port), "-j", "ACCEPT"])
  end

  # Allow DHCP
  System.cmd("iptables", ["-A", "INPUT", "-i", downstream, 
    "-p", "udp", "--dport", "67", "-j", "ACCEPT"])

  # Enable IP forwarding
  System.cmd("sysctl", ["-w", "net.ipv4.ip_forward=1"])

  gateway_access()
  internet_forwarding()
  internet_passthrough()
  dns_forwarding()
  set_dns_server(Tunneld.Servers.DnsConfig.get_dns_server())

  # NOW set DROP policies
  System.cmd("iptables", ["-P", "INPUT", "DROP"])
  System.cmd("iptables", ["-P", "FORWARD", "DROP"])
end

nftables is the successor to iptables, with cleaner syntax and better performance. However, iptables is universally available, has more documentation, and the commands are easier to script with System.cmd. Tunneld's rules are simple enough that nftables' advantages do not matter.

reset/0 flushes all rules and rebuilds from scratch. This is simpler than trying to detect and patch existing rules. It is called once at app start, not continuously, so the momentary rule absence is acceptable.

The code sets -P INPUT ACCEPT before adding rules, then sets -P INPUT DROP at the end. This prevents locking yourself out if an SSH session is open during deployment — the session survives because ESTABLISHED connections are allowed before the policy changes.

05 — Routing Tables & Egress

What Policy Routing Is

Standard routing decides where to send a packet based only on its destination address. Policy routing extends this: you can route based on source address, incoming interface, packet marking, or other criteria. This enables per-device or per-application routing decisions — essential for Tunneld's egress feature where different devices on the same subnet can exit through different remote machines.

Linux supports multiple routing tables. The default table (ID 254, called "main") is what ip route show displays. You can create additional tables (IDs 1-252) and define rules (ip rule) that select which table to use for which packets. This is called RPDB — the Routing Policy Database.

05 — Routing Tables & Egress

What Policy Routing Is (cont.)

Tunneld uses policy routing to implement "exit nodes": a device on the LAN can have its traffic routed through a remote VPS instead of the gateway's own upstream. Each exit machine gets its own routing table with a default route through its WireGuard tunnel, and ip rule entries steer specific devices' traffic to that table.

05 — Routing Tables & Egress

How Policy Routing Works · The Rule Lookup Process

When the kernel needs to route a packet, it walks through the RPDB in priority order. Each rule has a selector (what packets match) and an action (usually "lookup table N"). The first matching rule wins. 

# View the routing policy database:
$ ip rule show
0:      from all lookup local       # First: check local addresses
32766:  from all lookup main        # Then: check main routing table
32767:  from all lookup default     # Finally: check default table

# Rules are processed in priority order (lower number = higher priority)

05 — Routing Tables & Egress

How Policy Routing Works · Multiple Routing Tables

Each routing table is independent. You can have a different default gateway in each table. This is how Tunneld routes one device through a VPS while another uses the normal upstream. 

# The main table (254):
$ ip route show table main
default via 192.168.1.1 dev eth0   # Normal internet exit
10.0.0.0/24 dev eth1 scope link    # Local subnet

# A custom table (100) for an exit node:
$ ip route show table 100

10.0.0.0/24 dev eth1 scope link    # Keep local traffic local

The from selector matches the source IP of packets. By adding a rule from 10.0.0.50 lookup 100, all packets from device 10.0.0.50 will use table 100 (the exit node's table) instead of the main table.

Case Study: The with-chain Bug

The original code had a subtle bug: the with chain expected :ok from each step, but add_rule/2 and others returned {:ok, output}. The pattern mismatch caused the chain to short-circuit after the first step, never adding routes. This was found in production when devices lost internet after selecting an exit.

The fix: change patterns from :ok <- add_rule(...) to {:ok, _} <- add_rule(...). The lesson: in a with chain, every clause pattern must match the exact shape its function returns, or the chain falls through to the else branch and the remaining steps never run.

06 — Caddy Reverse Proxy

What a Reverse Proxy Is

A reverse proxy sits in front of backend servers and forwards client requests to them. Unlike a forward proxy (which clients configure to access the internet), a reverse proxy is transparent to clients — they think they are talking to the proxy, which handles routing to the actual backend.

Reverse proxies provide several benefits: load balancing across multiple backends, TLS termination (handling HTTPS so backends can be plain HTTP), hostname-based routing (multiple services on one port), health checking, request logging, and caching. For Tunneld, the key use is hostname-based routing: a single port 18000 serves all resources, with Caddy routing by the Host header.

06 — Caddy Reverse Proxy

What a Reverse Proxy Is (cont.)

Caddy is a modern web server and reverse proxy written in Go. It is notable for automatic HTTPS (via Let's Encrypt ACME), simple configuration, and a JSON admin API that allows runtime reconfiguration without restarts. Tunneld uses Caddy instead of nginx because it requires no config file template or reload signal — changes are atomic HTTP requests.

06 — Caddy Reverse Proxy

How Caddy Works · Host Header Routing

When a browser requests http://ollama.tunneld.lan:18000/api/generate, the HTTP request includes a Host: ollama.tunneld.lan header. Caddy matches this header against configured routes and proxies to the corresponding backend. Multiple services share port 18000 by having different hostnames.

...

# Caddy sees Host: ollama.tunneld.lan
# Looks up the route for that host
# Proxies to backend 10.0.0.50:11434

Caddy's admin API (default http://127.0.0.1:2019) allows you to inspect and modify the running configuration via HTTP. The most common endpoints:

07 — DNS, dnsmasq & DHCP

What DNS and DHCP Are

DNS (Domain Name System) translates human-readable names like google.com into IP addresses like 142.250.80.46. Without DNS, you would need to memorize IP addresses for every website. DNS is hierarchical: your device asks a resolver, which asks root servers, which delegate to TLD servers, which delegate to authoritative servers.

DHCP (Dynamic Host Configuration Protocol) automatically assigns IP addresses to devices when they join a network. Without DHCP, you would manually configure each device with an IP, subnet mask, gateway, and DNS server. DHCP also assigns the default gateway (option 3) and DNS servers (option 6).

07 — DNS, dnsmasq & DHCP

What DNS and DHCP Are (cont.)

dnsmasq is a lightweight program that provides both DNS forwarding and DHCP serving in one process. It is perfect for small networks: it caches DNS responses (speeding up repeated queries), serves local /etc/hosts entries, and can resolve custom domains. Tunneld uses dnsmasq to resolve *.tunneld.lan names and to assign IPs to devices on the subnet.

How DNS Works · DNS Record Types

DNS stores different types of records:

  • A — maps a name to an IPv4 address (example.com → 93.184.216.34)
  • AAAA — maps a name to an IPv6 address
  • CNAME — alias to another name (www.example.com → example.com)
  • MX — mail server for a domain
  • TXT — arbitrary text (used for verification, SPF, etc.)
  • NS — authoritative nameserver for a zone

# Query a specific nameserver:

How DNS Works · How DHCP Works (DORA)

DHCP uses a four-step handshake called DORA:

  1. Discover — client broadcasts "I need an IP" (UDP, src 0.0.0.0)
  2. Offer — server responds "Here's 10.0.0.50, want it?"
  3. Request — client broadcasts "Yes, I want 10.0.0.50"
  4. Acknowledge — server confirms "It's yours for N seconds"

The ACK includes options: subnet mask, default gateway (option 3), DNS servers (option 6), lease time, and more. When the lease expires, the client must renew or get a new address.

08 — SSH Transport

What SSH Is

SSH (Secure Shell) is a protocol for secure remote access to machines. It encrypts all traffic, authenticates both client and server, and provides a secure channel for running commands, transferring files, and forwarding ports. SSH replaced older insecure protocols like telnet and rsh.

For Tunneld, SSH is the actuation transport: every command that runs on a managed machine goes through SSH. When you click "Install WireGuard" in the dashboard, Tunneld SSHes into the machine and runs apt-get install wireguard-tools. When you view listeners, it runs ss -tlnp over SSH and parses the output.

08 — SSH Transport

What SSH Is (cont.)

SSH uses public-key cryptography for authentication. Each managed machine gets its own Ed25519 keypair, generated on the gateway. The operator installs the public key on the target's authorized_keys, and Tunneld uses the private key to authenticate. No passwords are stored.

08 — SSH Transport

How SSH Works · Key-Based Authentication

SSH keypairs work like a lock and key. The private key stays secret on the client (the gateway); the public key is installed on the server (the target). When connecting, the client proves it holds the private key without revealing it, using a cryptographic challenge-response. 

# Generate an Ed25519 keypair:
$ ssh-keygen -t ed25519 -C "tunneld" -f /tmp/my_key -N ""

$ cat /tmp/my_key.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBqK... tunneld

# Install on target:
$ echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBqK..." >> ~/.ssh/authorized_keys
$ chmod 600 ~/.ssh/authorized_keys

# Now connect using the private key:
$ ssh -i /tmp/my_key user@target

08 — SSH Transport

How SSH Works · Host Key Verification

The first time you connect to a server, SSH shows its fingerprint and asks if you trust it. This prevents man-in-the-middle attacks. Tunneld uses StrictHostKeyChecking=accept-new to automatically accept keys on first connection but reject changes.

08 — SSH Transport

How SSH Works · ControlMaster Multiplexing

Establishing an SSH connection involves a TCP handshake, key exchange, and authentication — slow for repeated commands. ControlMaster lets multiple SSH sessions share one underlying connection. The first connection creates a "master" socket; subsequent connections reuse it instantly. 

# SSH options for multiplexing:
ssh -o ControlMaster=auto \
    -o ControlPath=/tmp/ssh_%r@%h:%p \
    -o ControlPersist=600 \
    user@target "echo hello"

# First command: ~1 second (full connection)
# Subsequent commands: ~0.1 seconds (reuse master)

08 — SSH Transport

How Tunneld Uses SSH · Key Generation

When enrolling a machine, Tunneld generates an Ed25519 keypair and stores the private key under TUNNELD_DATA/ssh/<machine_id> (mode 0600).

def generate_keypair do
  tmp = Path.join(System.tmp_dir!(), "tunneld_key_#{System.unique_integer([:positive])}")

  {_, 0} = System.cmd("ssh-keygen", [
    "-t", "ed25519",
    "-N", "",           # No passphrase
    "-C", "tunneld",    # Comment
    "-f", tmp,
    "-q"                # Quiet
  ])

  {:ok, priv} = File.read(tmp)
  {:ok, pub} = File.read(tmp <> ".pub")
  File.rm(tmp)
  File.rm(tmp <> ".pub")
  {pub, priv}
end

def store_key(machine_id, priv_pem) do
  dir = ssh_dir()
  File.mkdir_p!(dir)
  path = key_path(machine_id)

  # Derive the public half from the private key so it can always be read back
  # (previously the .pub was never written, so the key vanished from the UI).
  pub = public_from_private(priv_pem)

  :ok = File.write(path, priv_pem)
  :ok = File.chmod(path, 0o600)
  :ok = File.write(path <> ".pub", pub)
  :ok = File.chmod(path <> ".pub", 0o644)
  :ok
end

defp real_run(machine, command, _opts) do
  id = machine["id"]
  key = key_path(id)
  host = machine["address"]
  user = machine["ssh_user"] || "root"
  port = to_string(machine["ssh_port"] || 22)

  args = [
    "-i", key,
    "-o", "StrictHostKeyChecking=accept-new",
    "-o", "ConnectTimeout=10",
    "-o", "ControlMaster=auto",
    "-o", "ControlPath=#{control_path(id)}",
    "-o", "ControlPersist=600",
    "-p", port,
    "#{user}@#{host}",
    command
  ]

  case System.cmd("ssh", args, stderr_to_stdout: true) do
    {out, 0} -> {:ok, out}
    {out, code} -> {:error, {:ssh_failed, code, out}}
  end
end

Why SSH · Why Not an Agent Daemon

Tunneld does not install an agent on each machine. Why? Because SSH already exists, is battle-tested, and does not require managing another process. An agent would need its own update mechanism, its own credentials, and would multiply the attack surface by the fleet size.

SSH gives you one key, one version, one audit trail. The gateway is the chokepoint — all commands flow through it. If you need exec capabilities on a machine, you POST /api/v1/agent/machines/:id/exec and the gateway SSHes in.

08 — SSH Transport

Ed25519 keys are short (256 bits), fast, and considered the most secure option available. RSA keys work but are larger (4096 bits for equivalent security) and slower to generate.

08 — SSH Transport

Why SSH · Why ControlMaster

Without multiplexing, every SSH.run/2 call would establish a new connection (~1 second). With ControlMaster, the first call creates a master connection, and subsequent calls reuse it (~0.1 seconds). This matters when probing a machine or running multiple commands in sequence.

09 — Elixir & OTP Supervision

What Elixir and OTP Are

Elixir is a functional programming language that runs on the BEAM virtual machine, the same VM that runs Erlang. The BEAM is designed for concurrent, distributed, fault-tolerant systems — it powers telecom switches, messaging systems, and databases that need to run forever without downtime.

OTP (Open Telecom Platform) is a set of libraries and design principles that come with Erlang/Elixir. The key abstraction is the process: lightweight, isolated units of execution that communicate via message passing. Unlike OS threads, BEAM processes are cheap (you can have millions) and isolated (one crashing does not affect others).

09 — Elixir & OTP Supervision

What Elixir and OTP Are (cont.)

The killer feature is supervision: processes can supervise other processes. If a child crashes, the supervisor restarts it. This enables the "let it crash" philosophy: instead of defensive coding, you write simple code and let the supervisor handle failures.

09 — Elixir & OTP Supervision

How OTP Works · Processes

A BEAM process is not an OS process — it is a lightweight execution unit managed by the VM. You can spawn millions of them. Each process has its own heap, mailbox, and runs independently. Processes communicate by sending messages to each other's mailboxes. 

# Spawn a process:
pid = spawn(fn -> 
  receive do
    {:greet, name} -> IO.puts("Hello, #{name}!")
  end
end)

# Send a message:
send(pid, {:greet, "World"})
# Output: Hello, World!

# The process exits after handling the message

09 — Elixir & OTP Supervision

How OTP Works · GenServer

GenServer is a behavior (like an interface) for processes that need to hold state and handle synchronous/asynchronous calls. Instead of writing raw receive loops, you implement callbacks: init/1, handle_call/3, handle_cast/2, handle_info/2. 

defmodule Counter do
  use GenServer

  # Client API
  def start_link(initial), do: GenServer.start_link(__MODULE__, initial, name: __MODULE__)
  def increment(), do: GenServer.call(__MODULE__, :increment)
  def get(), do: GenServer.call(__MODULE__, :get)

  # Server callbacks
  def init(initial), do: {:ok, initial}

  def handle_call(:increment, _from, count) do
    {:reply, count + 1, count + 1}
  end

  def handle_call(:get, _from, count) do
    {:reply, count, count}
  end
end

09 — Elixir & OTP Supervision

How OTP Works · Supervision Trees

A supervisor starts and monitors child processes. If a child crashes, the supervisor restarts it according to a strategy:

  • :one_for_one — restart only the crashed child
  • :one_for_all — restart all children if any crashes
  • :rest_for_one — restart the crashed child and all started after it
# Supervision tree definition:
children = [
  {Session, []},
  {Resources, []},
  {Devices, []}
]

opts = [strategy: :one_for_one, name: MyApp.Supervisor]
Supervisor.start_link(children, opts)

# If Resources crashes, only Resources is restarted
# Session and Devices continue running

Not everything is a GenServer. Overlay, Egress, Caddy, Reconcile and Machines (the machine registry and probe coordination) are plain modules with functions. # When to use a plain module:

# - Idempotent operations that read from external state

09 — Elixir & OTP Supervision

10 — Phoenix LiveView

What LiveView Is

Phoenix LiveView is a framework for building real-time, interactive web applications without writing JavaScript. The server renders HTML, sends it to the browser over a WebSocket, and when state changes, sends only the diff. User events (clicks, form submissions) are sent back over the same WebSocket, handled on the server, and the UI updates instantly.

This model inverts the typical SPA architecture. Instead of a JSON API + JavaScript frontend, you write Elixir functions that return HTML. State lives on the server. Interactivity is achieved through event handlers. The result is simpler code and faster development, at the cost of requiring a persistent WebSocket connection.

10 — Phoenix LiveView

What LiveView Is (cont.)

For Tunneld, LiveView enables a real-time dashboard where device lists, machine statuses, and resource health update automatically as the system state changes. PubSub broadcasts trigger re-renders, and users see updates without refreshing.

10 — Phoenix LiveView

How LiveView Works · The Lifecycle

A LiveView goes through several phases:

  1. HTTP GET — initial page load, mounts the LiveView, renders static HTML
  2. WebSocket connect — browser upgrades to WebSocket, LiveView re-mounts
  3. Live updates — events from user or PubSub trigger re-renders
  4. Termination — user navigates away, WebSocket closes

10 — Phoenix LiveView

How LiveView Works · The Lifecycle (cont.)

defmodule MyAppWeb.DashboardLive do
  use Phoenix.LiveView

  # Called on HTTP GET and WebSocket connect
  def mount(_params, _session, socket) do
    if connected?(socket) do
      # WebSocket is connected, subscribe to updates
      Phoenix.PubSub.subscribe(MyApp.PubSub, "updates")
    end

    {:ok, assign(socket, count: 0)}
  end

  # Renders HTML
  def render(assigns) do
    ~H"""
    <button phx-click="increment">Count: <%= @count %></button>
    """
  end

  # Handles user click
  def handle_event("increment", _params, socket) do
    {:noreply, assign(socket, count: socket.assigns.count + 1)}
  end

  # Handles PubSub broadcast
  def handle_info({:update, new_count}, socket) do
    {:noreply, assign(socket, count: new_count)}
  end
end

State is stored in the socket's assigns map. When you call assign(socket, key: value), LiveView tracks the change. On re-render, it computes the HTML diff and sends only the changed parts to the browser — not the entire page.

11 — Persistence & State

What Persistence Is

Persistence is how an application saves state across restarts. Most applications use databases (PostgreSQL, SQLite) to store data durably. Tunneld takes a simpler approach: JSON files on disk. Each domain has its own file: machines.json, resources.json, auth.json, etc.

The key principle is: remote state is authoritative, disk is a hint. The machines themselves know what is running (via ss -tlnp). Tunneld's JSON files record what was configured, but reconciliation reads live state and converges toward it.

This model trades query flexibility for simplicity. You cannot do complex queries across data. But the data is small (hundreds of records at most), reads are infrequent, and the operational complexity of a database on a resource-constrained SBC is avoided.

11 — Persistence & State

How JSON Persistence Works · Atomic Writes

A naive File.write! can corrupt data: if the process crashes mid-write, the file is truncated. Tunneld uses atomic writes: write to a temp file, then rename. The rename is atomic on POSIX filesystems — either the old or new file exists, never a partial write. 

# From lib/tunneld/persistence.ex:
def write_json(path, data) do
  encoded = Jason.encode!(data)
  tmp_path = path <> ".tmp"
  backup_path = path <> ".bak"

  # Backup current file if it exists
  if File.exists?(path) do
    File.copy(path, backup_path)
  end

  # Write to temp file, then atomic rename
  case File.write(tmp_path, encoded) do
    :ok ->
      File.rename(tmp_path, path)
    {:error, reason} ->
      File.rm(tmp_path)
      {:error, reason}
  end
end

11 — Persistence & State

How JSON Persistence Works · Backup Recovery

On read, if the main file is missing or corrupted, read_json/1 falls back to the .bak file. This handles cases where the main file is empty (disk full) or contains invalid JSON (cosmic ray?). 

# From lib/tunneld/persistence.ex:
def read_json(path) do
  case read_and_decode(path) do
    {:ok, data} -> {:ok, data}
    {:error, _} ->
      backup = path <> ".bak"
      case read_and_decode(backup) do
        {:ok, data} ->
          File.copy(backup, path)  # Restore from backup
          {:ok, data}
        error -> error
      end
  end
end

defp reconcile_wireguard(machine, repair?) do
  # Local machines have no overlay peer — short-circuit before probing.
  if machine["location"] == "local" do
    :ok
  else
    do_reconcile_wireguard(machine, repair?)
  end
end

defp do_reconcile_wireguard(machine, repair?) do
  case Overlay.status(machine) do
    {:ok, %{up: true}} -> :ok
    _ ->
      if repair? do
        case Overlay.ensure_peer(machine) do
          {:ok, _} -> {:repaired, :wireguard}
          {:error, reason} -> {:drift, {:wireguard_down, reason}}
        end
      else
        {:drift, :wireguard_down}
      end
  end
end

11 — Persistence & State

Why JSON Files · No Database Complexity

A database adds operational burden: backups, migrations, connection pooling, crash recovery. On an SBC with 2GB RAM, SQLite or PostgreSQL would compete with the application for resources. You would need to configure WAL mode, set up vacuum schedules, and handle migration failures gracefully.

PostgreSQL in particular requires a separate process (the postmaster) that consumes memory even when idle. SQLite is lighter but still requires careful handling of concurrent writes. JSON files with atomic rename have no concurrency issues because each write is a complete replacement of the file contents.

11 — Persistence & State

Why JSON Files · Human-Readable

JSON files can be inspected with cat and edited with a text editor. This is useful for debugging and manual recovery. When something goes wrong, you can SSH into the gateway, open resources.json in vim, and see exactly what the system thinks is configured. You can fix a typo, restart, and be done.

Try doing that with a PostgreSQL database. You would need to connect with psql, write SQL queries, and hope you understand the schema. The JSON approach makes the state completely transparent to operators.

11 — Persistence & State

Why JSON Files · The Data Is Small

A fleet of 100 machines is ~50KB of JSON. There is no performance reason for a database. Parsing 50KB takes milliseconds, and it happens only at startup and on writes. The overhead of a database connection pool would exceed the time saved on reads.

11 — Persistence & State

Why JSON Files · Remote State Is Authoritative

The most important reason is philosophical: disk state is a hint, not the truth. The real source of truth is the machines themselves. A machine knows what processes it is running via ss -tlnp. Tunneld's JSON records what was configured, but reconciliation always reads live state and converges toward it. If the JSON file is lost, Tunneld can re-probe machines and reconstruct most of the state.

This is different from an application where the database IS the truth. An e-commerce site cannot reconstruct orders from external systems. Tunneld can, because the external systems (the machines) have the real state.

12 — Agent API & Auth

What the Agent API Is

The Agent API is an HTTP interface for programmatic access to Tunneld. While the LiveView dashboard is for humans, the API is for scripts, CLIs, and AI agents. Operations like listing machines, creating resources, and running commands can be automated via curl or any HTTP client.

Authentication uses bearer tokens: API keys that are included in the Authorization header. Tokens are scoped (e.g., machines:read can list machines but not create them) and can be revoked at any time. This is more secure than username/password: tokens are single-purpose and revocable without changing credentials.

12 — Agent API & Auth

What the Agent API Is (cont.)

Long-running operations (like probing a machine over slow SSH) use the "jobs" pattern: the API returns 202 Accepted with a job ID immediately, and the client polls GET /api/v1/agent/jobs/:id for the result. This prevents HTTP timeouts.

12 — Agent API & Auth

How Token Auth Works · Token Format

Tokens are prefixed tnld_ for easy identification. This prefix serves several purposes:

  • Greppable — grep -r "tnld_" . finds all tokens in config files, scripts, and logs. Useful for auditing where tokens are stored.
  • Distinguishable — at a glance, you know a string is a Tunneld token and not an AWS key (AKIA...) or GitHub token (ghp_...).
  • Scannable — secret scanning tools (git-leaks, trufflehog) can be configured to detect tnld_ patterns and alert on committed tokens.
# Token format:
tnld_vG7hJ2mK8nP3qR9sT...

# The body after tnld_ is 24 random bytes, base64-encoded
# Total: ~40 characters, plenty of entropy

How Token Auth Works · Token Format (cont.)

The token body is 24 bytes of :crypto.strong_rand_bytes/1, URL-safe base64-encoded. This gives 192 bits of entropy — far more than needed. Brute-forcing a token would take longer than the heat death of the universe.

12 — Agent API & Auth

How Token Auth Works · Hashing at Rest

Tokens are stored as SHA-256 hashes, not plaintext. When you issue a token, the raw token is returned once and never stored. If someone steals tokens.json, they get hashes, not usable tokens. 

# From lib/tunneld/agent_tokens.ex:
def handle_call({:issue, scopes}, _from, state) do
  # Strip any forbidden scopes defensively.
  clean = scopes -- forbidden_scopes()
  raw = @prefix <> Base.url_encode64(:crypto.strong_rand_bytes(24), padding: false)
  id = :crypto.strong_rand_bytes(8) |> Base.url_encode64(padding: false)

  record = %{
    "id" => id,
    "hash" => hash(raw),  # SHA-256, not plaintext!
    "scopes" => clean,
    "created_at" => DateTime.utc_now() |> DateTime.to_iso8601()
  }

  write(path(), read() |> Map.put(id, record))
  {:reply, {:ok, raw, id, clean}, state}  # raw returned once
end

defp hash(raw), do: :crypto.hash(:sha256, raw) |> Base.encode16(case: :lower)

How Tunneld Uses the API · The Jobs Pattern

The golden rule: never block an HTTP request on a 60-second SSH call. Probing a machine over a slow connection can take 30-60 seconds. Installing WireGuard involves apt-get, which can take minutes. If the API handler waited for these operations, the HTTP client would time out, load balancers would kill the connection, and users would see failures even when the operation succeeded.

The jobs pattern solves this: long operations return 202 Accepted immediately with a job ID. The work runs in a background process. The client polls GET /api/v1/agent/jobs/:id until the status changes from running to done.

Why This Design · Why Not Session Cookies

Session cookies work for browser-based auth but not for scripts or agents. Bearer tokens are stateless, can be stored in config files, and work with any HTTP client. A cron job or CI pipeline cannot maintain a browser session, but it can read a token from an environment variable and pass it in headers.

Tokens also enable multi-tenant access patterns. An operator can issue a monitoring token to an observability platform and a deployment token to a CI system. Each has exactly the permissions it needs, and revoking one does not affect the other. Session cookies do not support this model elegantly.

12 — Agent API & Auth

Why This Design · Why Scopes

A read-only token for monitoring should not be able to delete machines. Scopes implement the principle of least privilege. If a monitoring service is compromised, the attacker can only read data, not modify it. The blast radius is limited by the token's capabilities.

Scopes also enable audit clarity. When reviewing logs, you can see which token performed each action and know immediately whether it had the authority to do so. A token with only resources:read should never appear in a machines:write audit entry.

12 — Agent API & Auth

Why This Design · Why Hashing at Rest

If an attacker gains read access to the gateway's filesystem (via a vulnerability or backup leak), they get tokens.json. With plaintext tokens, they could impersonate any API client. With hashes, they get nothing usable — the tokens cannot be reversed from the hashes.

This is standard practice for password storage (bcrypt for passwords, SHA-256 for tokens). The difference is that tokens are high-entropy random values, so SHA-256 is sufficient. Passwords need slow hashing (bcrypt) because users choose weak passwords that can be dictionary-attacked.

12 — Agent API & Auth

Why This Design · Why No Agent on Targets

An agent daemon on each machine would need its own credentials, update mechanism, and security surface. SSH already exists and is auditable from the gateway. Installing an agent multiplies the credential surface by the fleet size: each machine holds credentials that could be stolen.

The chokepoint model is more secure. All commands flow through the gateway, which holds one set of credentials (the SSH keys), maintains one audit log, and enforces one set of policies. Compromising a managed machine does not give access to other machines because the SSH keys live on the gateway, not the targets.

13 — Build, Release & Deploy

What a Mix Release Is

A Mix release is a self-contained package of your Elixir application and the Erlang runtime (ERTS). It can be deployed to a target machine without installing Elixir or Erlang — everything needed to run is bundled. This is how Tunneld runs on the gateway SBC.

The release includes: compiled BEAM bytecode (.beam files), the Erlang VM binary, boot scripts, and configuration. It is a tarball that you extract, configure, and run. No compilation happens on the target.

Cross-compilation is necessary because Tunneld is developed on x86_64 macOS/Linux but deployed on ARM64 Debian. The release must be built for the target architecture, not the development machine.

How Releases Work · ERTS Bundling and glibc Compatibility

The release bundles ERTS (Erlang Run-Time System) — the BEAM VM binary. This binary is compiled for a specific architecture (ARM64) and links against the system's glibc. Here is where things get tricky:

glibc is backward-compatible but not forward-compatible. If you build the release on a system with glibc 2.36, it will NOT run on a system with glibc 2.31. The error is cryptic: GLIBC_2.36 not found.

The solution: build on an OS version older than or equal to your targets. If your SBCs run Debian 11 (glibc 2.31), build in a Debian 11 container. A Debian 12 build (glibc 2.36) will not run on Debian 11.

Why Mix Releases · No Runtime Dependencies

The gateway does not need Elixir or Erlang installed. The release bundles ERTS, so it runs on any Linux with glibc. 13 — Build, Release & Deploy

Why Mix Releases · Reproducible Deploys

The release tarball is a single artifact. Deploy the same tarball to dev, staging, and prod. No "works on my machine" issues from different Elixir versions. The exact bytes that passed CI are the exact bytes that run in production.

This reproducibility extends to debugging. If a bug appears in production, you can download the exact tarball, extract it locally, and debug with confidence that you are looking at the same code. There is no drift between environments.

13 — Build, Release & Deploy

Why Mix Releases · Fast Startup

Releases start faster than mix phx.server because there is no compilation step. The BEAM loads precompiled bytecode directly. On an SBC with slow storage, this difference is noticeable: seconds instead of tens of seconds.

Fast startup also improves recovery from crashes. With Restart=on-failure in the systemd unit, a crashed Tunneld restarts within seconds. If compilation were involved, the restart would be slow enough to affect users.

13 — Build, Release & Deploy

Why Mix Releases · Versioned Rollbacks

Each release tarball has a version number. If a deploy breaks something, you can roll back to the previous tarball instantly. Keep the last few tarballs on the gateway, and rollback is just extracting an older one and restarting.

This is simpler than Git-based rollbacks, which would require re-compiling the old code. With tarballs, the old code is already compiled and ready to run.

14 — Testing & Mock Mode

What Mock Mode Is

Mock mode (MOCK_DATA=true) allows Tunneld to run on a development machine without real hardware or SSH targets. System commands (iptables, systemctl, ssh) are stubbed, and fake data is provided for DHCP leases, ethernet link state, and machine probes.

This enables development on macOS or any Linux workstation without an SBC. The full enroll → probe → expose flow works, just with simulated responses. The dashboard is fully functional, you just cannot actually route packets.

ExUnit is Elixir's testing framework. Tunneld's tests use mock mode to verify business logic without needing real machines. Tests cover machine enrollment, overlay IP allocation, egress routing, and API endpoints.

15 — systemd Service Lifecycle

What systemd Is

systemd is the init system and service manager for most modern Linux distributions. It starts services at boot, manages dependencies between them, restarts crashed services, and provides logging via journald. Every long-running process on a Debian system is typically a systemd service.

Tunneld itself runs as a systemd service (tunneld.service). It also manages other services: dnsmasq, caddy, and per-machine WireGuard interfaces (wg-quick@). Understanding systemd is essential for debugging service failures and configuring automatic restarts.

A systemd unit file describes how to start, stop, and monitor a service. Unit files live in /etc/systemd/system/ (admin-created) or /lib/systemd/system/ (package-provided). The systemctl command controls services.

15 — systemd Service Lifecycle

How systemd Works · Unit Files

A unit file has three sections: [Unit] (metadata, dependencies), [Service] (how to run), and [Install] (how to enable).

The unit below is the one written by the separate tunneld-installer repo — nothing in this codebase emits it, so treat it as illustrative of what the installer lays down rather than as a file you will find in this repo. 

# /etc/systemd/system/tunneld.service (as written by the installer)
[Unit]
Description=Tunneld Gateway
After=network.target

[Service]
Type=exec
User=root
WorkingDirectory=/opt/tunneld
Environment=SECRET_KEY_BASE=abc123...
Environment=UPSTREAM_INTERFACE=eth0
Environment=DOWNSTREAM_INTERFACE=eth1
ExecStart=/opt/tunneld/bin/tunneld start
ExecStop=/opt/tunneld/bin/tunneld stop
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

15 — systemd Service Lifecycle

How systemd Works · Enable vs Start

enable creates symlinks so the service starts at boot. start starts it now. You usually do both: 

# Enable at boot AND start now:
$ systemctl enable --now tunneld

# Just start (won't survive reboot):
$ systemctl start tunneld

# Just enable (won't start until reboot):
$ systemctl enable tunneld

15 — systemd Service Lifecycle

How systemd Works · Service Types

The Type= directive tells systemd how to determine when the service is "started" — a critical distinction for dependency ordering and readiness checks.

15 — systemd Service Lifecycle

How systemd Works · Service Types (cont.)

  • simple — systemd considers it started as soon as ExecStart runs. The process is assumed ready immediately. Fast but imprecise: the service might not actually be listening on its port yet.
  • exec — like simple, but waits for the exec() syscall to succeed before reporting started. Slightly more accurate: catches immediate exec failures.
  • forking — the process forks and the parent exits (daemon style). systemd waits for the parent to exit before reporting started. Use PIDFile= to track the child.
  • notify — the process explicitly signals readiness via sd_notify(). Most accurate: the service reports when it is truly ready to accept connections. The BEAM supports this via :systemd.notify/1.
  • oneshot — runs once and exits (like a script). Useful for setup tasks. The service is "started" after the process exits successfully.

15 — systemd Service Lifecycle

How systemd Works · Service Types (cont.)

The installer's tunneld.service uses exec. WireGuard's wg-quick@ uses oneshot because it sets up the interface and exits — the interface persists after the script completes.

15 — systemd Service Lifecycle

How systemd Works · Templated Units (wg-quick@)

A unit file with @ in its name is a template. The part after @ is substituted into the unit via %i. This allows one unit file to manage many instances. 

# /lib/systemd/system/wg-quick@.service (provided by wireguard-tools):
[Unit]
Description=WireGuard via wg-quick(8) for %I
After=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/wg-quick up %i
ExecStop=/usr/bin/wg-quick down %i

[Install]
WantedBy=multi-user.target

# When you run: systemctl start wg-quick@wg-d4f4632f
# %i becomes "wg-d4f4632f"
# ExecStart becomes: /usr/bin/wg-quick up wg-d4f4632f
# Which reads: /etc/wireguard/wg-d4f4632f.conf

15 — systemd Service Lifecycle

How systemd Works · Templated Units (wg-quick@) (cont.)

Tunneld creates one WireGuard interface per machine. Each interface is managed by an instance of the templated unit: wg-quick@wg-abc123, wg-quick@wg-def456, etc. This is why Overlay.install_target/3 runs systemctl enable --now wg-quick@#{iface}.

Why systemd · Automatic Restart

Crashes happen. Restart=on-failure means the service recovers automatically without human intervention. The RestartSec=5 directive adds a 5-second delay between restarts to prevent tight crash loops.

Note the difference between restart policies:

  • Restart=no — never restart (default)
  • Restart=on-failure — restart only on non-zero exit or signal
  • Restart=always — restart even on clean exit (useful for services that should never stop)
  • Restart=on-abnormal — restart on signal, timeout, or watchdog, but not on clean exit or non-zero exit code

Tunneld uses on-failure because a clean exit (e.g., from bin/tunneld stop) should not trigger a restart, but a crash or OOM-kill should.

Why systemd · Enable vs Start

A common confusion: systemctl enable and systemctl start are different operations.

  • enable — create symlinks so the service starts at boot. Does NOT start the service now. The service will start on next reboot.
  • start — start the service now. Does NOT persist across reboot. If the machine reboots, the service will not start unless it is also enabled.
  • enable --now — do both: enable for boot AND start now. This is what you usually want.
# Just enable (start on next boot):
$ systemctl enable tunneld
# Service is NOT running yet

# Just start (does not persist):
$ systemctl start tunneld
# Service is running, but won't start after reboot

# Enable AND start:
$ systemctl enable --now tunneld
# Service is running AND will start on reboot

16 — Pooling & Load Balancing

What Pooling Is

A pool is a set of backend servers that can handle requests for a resource. Instead of pointing a resource at a single server, you point it at a pool. The reverse proxy (Caddy) distributes requests across pool members, providing redundancy and increased capacity.

Load balancing is the strategy for distributing requests. Common strategies include round-robin (rotate through backends), least-connections (send to the least busy), and random. Caddy defaults to round-robin, which is sufficient for most cases.

Health checking monitors pool members and removes unhealthy ones from rotation. If a backend stops responding, requests stop going to it until it recovers. This is essential for high availability.

16 — Pooling & Load Balancing

How Load Balancing Works · Load Balancing Policies

Caddy supports several load balancing policies via lb_policy:

  • round_robin (default) — rotate through backends in order
  • random — pick a backend at random
  • least_conn — send to the backend with fewest active connections
  • first — always use the first healthy backend (failover mode)
  • ip_hash — hash the client IP to pick a backend (sticky sessions)
  • uri_hash — hash the request URI to pick a backend (cache-friendly)
  • header — hash a specific header value
  • cookie — use a cookie for sticky sessions

Tunneld uses the default round_robin. For AI inference backends like Ollama, least_conn might be better because inference requests have varying duration — a 30-second generation should not block other requests on that backend while others are idle.

16 — Pooling & Load Balancing

How Load Balancing Works · Passive vs Active Health Checks

Passive health checks (Caddy's default) detect failures from real traffic. If a request to a backend times out or returns a 5xx error, that backend is marked unhealthy. No extra probes are sent; the check is "passive" because it observes real requests.

The downside: the first user after a backend dies gets an error. You do not discover the failure until someone hits it.

Active health checks send periodic probe requests (e.g., GET /health every 10 seconds) even when no user traffic is flowing. This detects failures before users hit them, at the cost of extra network traffic.

def pool_health(pool, false) when is_list(pool) do
  totals =
    pool
    |> Enum.map(&String.trim/1)
    |> Enum.reject(&(&1 == ""))
    |> Enum.reduce(%{total: 0, up: 0}, fn entry, acc ->
      case String.split(entry, ":", parts: 2) do
        [ip, port_str] ->
          total = acc.total + 1
          up = case Integer.parse(port_str) do
            {port, _} -> if backend_up?(ip, port), do: acc.up + 1, else: acc.up
            _ -> acc.up
          end
          %{acc | total: total, up: up}
        _ -> acc
      end
    end)

  status = cond do
    totals.total == 0 -> :empty
    totals.up == 0 -> :none
    totals.up == totals.total -> :all_up
    true -> :partial
  end

  Map.put(totals, :status, status)
end

defp backend_up?(ip, port) do
  case :gen_tcp.connect(String.to_charlist(ip), port, [:binary, active: false], 1500) do
    {:ok, socket} -> :gen_tcp.close(socket); true
    _ -> false
  end
end

18 — Terminal Exec

What Terminal Exec Is

Terminal Exec is Tunneld's interactive SSH terminal feature. It streams a full PTY session from a managed machine directly into the browser, letting operators type commands and see output in real time. The architecture is: browser → Phoenix channel → gateway → Erlang :ssh → target machine. The browser never touches the SSH connection directly; all credentials stay on the gateway.

Unlike the POST /api/v1/agent/machines/:id/exec API endpoint which runs a single command and returns output, the terminal maintains a persistent interactive session. The operator sees a real shell prompt, can run htop, vim, or any interactive program. Resize events propagate through the channel so the PTY dimensions stay in sync with the browser window.

18 — Terminal Exec

What Terminal Exec Is (cont.)

The frontend uses xterm.js, a terminal emulator written in TypeScript. The gateway uses Erlang's built-in :ssh module (shipped with OTP) to open a connection and allocate a PTY. Data flows bidirectionally over a Phoenix channel: keystrokes from the browser are sent as "data" pushes, and output from the remote shell is base64-encoded and pushed as "data" events to the browser.

Security is enforced at two points: socket connect and channel join. The operator must have a valid dashboard session (verified from the HttpOnly cookie). The SSH keys that authenticate to the target machine never leave the gateway; the browser only sees terminal I/O. Session open and close events are logged to the audit log, but individual commands within the session are not captured — an honest limitation documented below.

18 — Terminal Exec

How It Works · The Channel Flow

When the operator clicks "Terminal" on a machine card, the LiveView renders a hook element with data-machine-id. The TerminalHook JavaScript mounts, creates an xterm.js terminal, and opens a Phoenix socket to /ws. It then joins the channel exec:<machine_id>.

On the server, TunneldWeb.ExecChannel.join/3 verifies the session, looks up the machine, and starts a linked Tunneld.Machines.SSH.Session GenServer. That GenServer calls :ssh.connect/4 to the target (via the WireGuard overlay address), allocates a PTY, and starts a shell. The channel pushes "connected" to the browser, which focuses the terminal.

18 — Terminal Exec

How It Works · The Channel Flow (cont.)

From then on, keystrokes flow browser → channel → GenServer → SSH connection, and output flows SSH connection → GenServer → channel → browser. The GenServer receives {:ssh_cm, conn, {:data, channel_id, type, data}} messages from the Erlang SSH library and forwards them to the channel via send/2.

The channel calls Session.resize/3, which issues a :ssh_connection.window_change/6 to the target. This keeps the remote PTY in sync with the browser terminal, so full-screen programs render correctly.

How Tunneld Uses It · SSH via user_dir

Erlang's :ssh.connect/4 authenticates using keys in a user_dir directory. The Session GenServer creates a temporary directory with the machine's private key copied in as id_ed25519 (mode 0600). This is cleaned up on termination. 

# From lib/tunneld/machines/ssh/session.ex:
defp setup_user_dir(key_path) do
  nonce = :crypto.strong_rand_bytes(8) |> Base.encode16(case: :lower)
  user_dir = Path.join(System.tmp_dir!(), "tunneld_ssh_#{nonce}")

  try do
    File.mkdir_p!(user_dir)
    File.chmod!(user_dir, 0o700)

    # Copy the private key as id_ed25519
    dest = Path.join(user_dir, "id_ed25519")
    File.cp!(key_path, dest)
    File.chmod!(dest, 0o600)

    {:ok, user_dir}
  rescue
    e -> {:error, {:user_dir_setup_failed, Exception.message(e)}}
  end
end

How Tunneld Uses It · Audit Logging

Every session open and close is logged via Tunneld.Audit.log/4. The log includes the machine ID, result (started/closed/failed), and the operator's client ID. This creates an audit trail of who had shell access to which machine and when.

Honest limitation: Individual commands within the PTY session are not captured. Unlike POST /machines/:id/exec, where the command string is logged, an interactive session streams raw terminal I/O. Logging that would require parsing escape sequences and reconstructing lines, which is fragile and privacy-invasive. Tunneld logs session boundaries only.

Why (And Three Bugs Found in Production) · Bug 1: user_dir vs. Key Callback

An earlier version used a custom :key_cb callback to provide the private key to Erlang's :ssh client. It negotiated SSH fine, then failed during userauth for OpenSSH-format ed25519 keys. The error was cryptic: :no_auth_method. Switching to user_dir containing id_ed25519 (mode 0600) worked immediately.

Lesson: Prefer the library's standard mechanism over a bespoke callback. The key_cb interface is designed for HSMs and custom key formats, not for reading a file that the library already knows how to read. The user_dir path is battle-tested and handles OpenSSH format correctly.

Why (And Three Bugs Found in Production) · Bug 2: _csrf_token Required for Session

Phoenix only populates connect_info[:session] when the socket handshake includes a valid _csrf_token parameter. Without it, connect_info.session is nil, and the socket connect function refused with 403 (no client_id to validate).

The fix was simple: pass the CSRF token from the meta tag when creating the socket. LiveView's own socket does the same thing; this is documented behaviour, just easy to overlook. 

// From assets/js/terminal_hook.js:

  .querySelector("meta[name='csrf-token']")
  ?.getAttribute("content");

const socket = new window.Phoenix.Socket("/ws", {
  params: { _csrf_token: csrfToken },
});

Why (And Three Bugs Found in Production) · Bug 3: phx-update="ignore"

xterm.js injects its own DOM into the hook element: a viewport, a screen, cursor layers. Without phx-update="ignore" on the container, LiveView's next diff reconciled that subtree back to the empty server-rendered div. The terminal silently vanished a few seconds after mounting.
