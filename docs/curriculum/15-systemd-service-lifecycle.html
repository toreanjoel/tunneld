15 — systemd Service Lifecycle

Key source: lib/tunneld/servers/services.ex, lib/tunneld/overlay.ex

What systemd Is

systemd is the init system and service manager for most modern Linux distributions. It starts services at boot, manages dependencies between them, restarts crashed services, and provides logging via journald. Every long-running process on a Debian system is typically a systemd service.

Tunneld itself runs as a systemd service (tunneld.service). It also manages other services: dnsmasq, caddy, and per-machine WireGuard interfaces (wg-quick@). Understanding systemd is essential for debugging service failures and configuring automatic restarts.

A systemd unit file describes how to start, stop, and monitor a service. Unit files live in /etc/systemd/system/ (admin-created) or /lib/systemd/system/ (package-provided). The systemctl command controls services.

How systemd Works

Unit Files

A unit file has three sections: [Unit] (metadata, dependencies), [Service] (how to run), and [Install] (how to enable).

The unit below is the one written by the separate tunneld-installer repo — nothing in this codebase emits it, so treat it as illustrative of what the installer lays down rather than as a file you will find in this repo. 

# /etc/systemd/system/tunneld.service (as written by the installer)
[Unit]
Description=Tunneld Gateway
After=network.target

[Service]
Type=exec
User=root
WorkingDirectory=/opt/tunneld
Environment=SECRET_KEY_BASE=abc123...
Environment=UPSTREAM_INTERFACE=eth0
Environment=DOWNSTREAM_INTERFACE=eth1
ExecStart=/opt/tunneld/bin/tunneld start
ExecStop=/opt/tunneld/bin/tunneld stop
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Enable vs Start

enable creates symlinks so the service starts at boot. start starts it now. You usually do both: 

# Enable at boot AND start now:
$ systemctl enable --now tunneld

# Just start (won't survive reboot):
$ systemctl start tunneld

# Just enable (won't start until reboot):
$ systemctl enable tunneld

Service Types

The Type= directive tells systemd how to determine when the service is "started" — a critical distinction for dependency ordering and readiness checks.

  • simple — systemd considers it started as soon as ExecStart runs. The process is assumed ready immediately. Fast but imprecise: the service might not actually be listening on its port yet.
  • exec — like simple, but waits for the exec() syscall to succeed before reporting started. Slightly more accurate: catches immediate exec failures.
  • forking — the process forks and the parent exits (daemon style). systemd waits for the parent to exit before reporting started. Use PIDFile= to track the child.
  • notify — the process explicitly signals readiness via sd_notify(). Most accurate: the service reports when it is truly ready to accept connections. The BEAM supports this via :systemd.notify/1.
  • oneshot — runs once and exits (like a script). Useful for setup tasks. The service is "started" after the process exits successfully.

The installer's tunneld.service uses exec. WireGuard's wg-quick@ uses oneshot because it sets up the interface and exits — the interface persists after the script completes.

Templated Units (wg-quick@)

A unit file with @ in its name is a template. The part after @ is substituted into the unit via %i. This allows one unit file to manage many instances. 

# /lib/systemd/system/wg-quick@.service (provided by wireguard-tools):
[Unit]
Description=WireGuard via wg-quick(8) for %I
After=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/wg-quick up %i
ExecStop=/usr/bin/wg-quick down %i

[Install]
WantedBy=multi-user.target

# When you run: systemctl start wg-quick@wg-d4f4632f
# %i becomes "wg-d4f4632f"
# ExecStart becomes: /usr/bin/wg-quick up wg-d4f4632f
# Which reads: /etc/wireguard/wg-d4f4632f.conf

Tunneld creates one WireGuard interface per machine. Each interface is managed by an instance of the templated unit: wg-quick@wg-abc123, wg-quick@wg-def456, etc. This is why Overlay.install_target/3 runs systemctl enable --now wg-quick@#{iface}.

Journald Logging

systemd captures stdout/stderr from services and stores them in the journal. Use journalctl to view logs: 

# Logs for a specific service:
$ journalctl -u tunneld

# Follow logs in real-time:
$ journalctl -u tunneld -f

# Last 100 lines:
$ journalctl -u tunneld -n 100

# Logs since boot:
$ journalctl -u tunneld -b

How Tunneld Uses systemd

Checking Service Status

lib/tunneld/servers/services.ex monitors dnsmasq, caddy, and dhcpcd: 

# From lib/tunneld/servers/services.ex:
defp check_service(service) do
  try do
    {output, _exit_code} = System.cmd("systemctl", ["is-active", service |> to_string])
    is_active = String.trim(output) == "active"

    if !is_active do
      System.cmd("systemctl", ["start", service |> to_string])
    end

    is_active
  rescue
    _ ->
      false
  end
end

Note that check_service/1 does two things: it checks status AND auto-starts the service if inactive. This is called every 10 seconds via the GenServer's :sync handler, ensuring core services stay running.

WireGuard Interfaces

Each WireGuard interface uses a template unit: wg-quick@.service. The part after @ is the interface name: 

# From lib/tunneld/overlay.ex (install_target/3, abridged):
defp install_target(machine, target_pub, iface) do
  _ = target_pub

  # 1. Install wireguard-tools if missing (apt/dnf/apk), so wg-quick exists.
  run(
    machine,
    "command -v wg-quick >/dev/null 2>&1 || " <>
      "(command -v apt-get >/dev/null 2>&1 && apt-get update -qq && apt-get install -y -qq wireguard-tools) || " <>
      "(command -v dnf >/dev/null 2>&1 && dnf install -y wireguard-tools) || " <>
      "(command -v apk >/dev/null 2>&1 && apk add wireguard-tools) || true"
  )

  # 2. Enable + start the wg-quick unit for this peer. The trailing
  #    `2>/dev/null || true` keeps enrollment going on hosts without systemd.
  run(machine, "systemctl enable --now wg-quick@#{iface} 2>/dev/null || true")

  # 3. Open the overlay port on the target's own firewall.
  run(
    machine,
    "ufw allow 51821/udp 2>/dev/null || " <>
      "iptables -I INPUT 1 -p udp --dport 51821 -j ACCEPT 2>/dev/null || true"
  )

  :ok
end

# The config file is /etc/wireguard/wg-d4f4632f.conf, so the unit instance is
# systemctl enable --now wg-quick@wg-d4f4632f

Restart Policy

The tunneld.service unit written by the installer uses Restart=on-failure: if the release crashes, systemd restarts it after RestartSec=5. This provides automatic recovery from transient failures. (The unit lives in the installer repo, not here, so confirm the exact directives against the installed file on your gateway.)

Why systemd

Standard on Debian

Every Debian system (the target OS) uses systemd. Learning it is not optional for Linux system administration. The alternatives (sysvinit, upstart, runit) are either deprecated or niche. systemd is the reality.

Dependency Management

After=network.target ensures Tunneld starts after networking is up. Without this, the app might fail to bind to interfaces. You can express complex dependencies: "start A after B and C are running, but only if D is not running."

Automatic Restart

Crashes happen. Restart=on-failure means the service recovers automatically without human intervention. The RestartSec=5 directive adds a 5-second delay between restarts to prevent tight crash loops.

Note the difference between restart policies:

  • Restart=no — never restart (default)
  • Restart=on-failure — restart only on non-zero exit or signal
  • Restart=always — restart even on clean exit (useful for services that should never stop)
  • Restart=on-abnormal — restart on signal, timeout, or watchdog, but not on clean exit or non-zero exit code

Tunneld uses on-failure because a clean exit (e.g., from bin/tunneld stop) should not trigger a restart, but a crash or OOM-kill should.

Enable vs Start

A common confusion: systemctl enable and systemctl start are different operations.

  • enable — create symlinks so the service starts at boot. Does NOT start the service now. The service will start on next reboot.
  • start — start the service now. Does NOT persist across reboot. If the machine reboots, the service will not start unless it is also enabled.
  • enable --now — do both: enable for boot AND start now. This is what you usually want.
# Just enable (start on next boot):
$ systemctl enable tunneld
# Service is NOT running yet

# Just start (does not persist):
$ systemctl start tunneld
# Service is running, but won't start after reboot

# Enable AND start:
$ systemctl enable --now tunneld
# Service is running AND will start on reboot

Examples

Manage the tunneld service

# Check status:
$ systemctl status tunneld
● tunneld.service - Tunneld Gateway
   Loaded: loaded (/etc/systemd/system/tunneld.service; enabled)
   Active: active (running) since ...

# Restart:
$ systemctl restart tunneld

# Stop:
$ systemctl stop tunneld

# View logs:
$ journalctl -u tunneld -f

Debug a failing service

# Check why it failed:
$ systemctl status tunneld
# Look for "Active: failed" and the reason

# View full logs:
$ journalctl -u tunneld -n 50

# Common issues:
# - Missing environment variables
# - Port already in use
# - File permissions

Manage WireGuard interfaces

# List all wg-quick services:
$ systemctl list-units 'wg-quick@*'

# Restart a specific interface:
$ systemctl restart wg-quick@wg-d4f4632f

# View WireGuard logs:
$ journalctl -u wg-quick@wg-d4f4632f

Reload after changing unit files

# After editing /etc/systemd/system/tunneld.service:
$ systemctl daemon-reload
$ systemctl restart tunneld
