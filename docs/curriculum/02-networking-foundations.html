02 — Networking Foundations

Key source: lib/tunneld/iptables.ex, lib/tunneld/net_link.ex, lib/tunneld/overlay.ex

What Networking Is

Networking is how computers find and talk to each other. At its core, every device on a network has an address (like a phone number), and data is broken into packets that travel from source to destination through intermediate devices. The rules for how this works are layered: at the bottom, raw electrical signals; at the top, applications like web browsers.

Tunneld operates primarily at layers 3 and 4 of the OSI model: the network layer (IP addressing, routing) and the transport layer (TCP/UDP, ports). Understanding these layers is essential because Tunneld manipulates IP addresses, routes packets between networks, and exposes services bound to specific ports.

The key concepts you need to understand are: IP addresses (how devices are identified), subnets (how addresses are grouped), routing (how packets find their way), NAT (how private addresses reach the public internet), ports (how multiple services share one IP), and sockets (how applications bind to addresses and ports).

How Networking Works

IP Addresses

An IPv4 address is a 32-bit number, written as four octets separated by dots: 192.168.1.50. Each octet ranges from 0 to 255. This gives about 4.3 billion possible addresses — not enough for every device, which is why NAT and private addresses exist.

Private address ranges (RFC 1918) are reserved for local networks and are not routable on the public internet:

  • 10.0.0.0/8 — 16 million addresses
  • 172.16.0.0/12 — 1 million addresses
  • 192.168.0.0/16 — 65,536 addresses

Tunneld does not hardcode a LAN subnet: the gateway's own address comes from the GATEWAY environment variable (config/runtime.exs raises in production if it is missing), and the subnet is derived from it. The examples on this page use 10.0.0.0/24 with the gateway at 10.0.0.1. The overlay subnet for WireGuard is 10.88.0.0/24. Both are private ranges. 

# Example: reading the gateway IP in lib/tunneld/config.ex
def network(key) do
  case Application.get_env(:tunneld, :network, []) do
    kw when is_list(kw) -> Keyword.get(kw, key)
    map when is_map(map) -> Map.get(map, key) || Map.get(map, to_string(key))
    _ -> nil
  end
end

def gateway_ip, do: network(:gateway)  # e.g., "10.0.0.1"

Subnets and CIDR Notation

A subnet is a logical division of an IP network. CIDR notation (10.0.0.0/24) specifies the network prefix length — how many bits identify the network vs. the host. /24 means the first 24 bits are the network portion, leaving 8 bits (256 addresses) for hosts. 

# CIDR examples:
10.0.0.0/24    = 10.0.0.0   to 10.0.0.255   (256 addresses)
10.0.0.0/16    = 10.0.0.0   to 10.0.255.255 (65,536 addresses)
10.88.0.0/24   = 10.88.0.0  to 10.88.0.255  (Tunneld overlay subnet)

# The /24 is called the "subnet mask" or "prefix length"
# In dotted form: /24 = 255.255.255.0

Two devices are on the "same subnet" if their network portions match. In lib/tunneld/overlay.ex, the same_subnet?/1 function checks this by comparing the first three octets (for a /24): 

# From lib/tunneld/overlay.ex:
defp same_subnet?(address) do
  gw = Tunneld.Config.gateway_ip()  # e.g., "10.0.0.1"
  with {:ok, a} <- parse_ip4(address),
       {:ok, g} <- parse_ip4(gw) do
    match?({[x, y, z, _], [x, y, z, _]}, {a, g})  # First 3 octets match
  else
    _ -> false
  end
end

Routing

Routing is how packets find their way from source to destination. Every device has a routing table that says "packets for network X go out interface Y (optionally via gateway Z)." When a packet arrives, the kernel consults this table to decide what to do.

The most important route is the default gateway: where to send packets when no more specific route matches. On Tunneld's subnet, every device's default gateway is the Tunneld box itself (10.0.0.1). This is set via DHCP option 3. 

# Viewing the routing table on Linux:
$ ip route show
default via 10.0.0.1 dev eth0 proto dhcp metric 100
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.50
10.88.0.0/24 dev wg-d4f4632f proto kernel scope link

# Reading: "default" = any destination not matched below
# "via 10.0.0.1" = send to the gateway
# "dev eth0" = out this interface

NAT (Network Address Translation)

NAT allows devices on a private subnet to reach the public internet using the gateway's public IP. The gateway rewrites the source IP of outgoing packets (from the private address to its own public address) and remembers the mapping so replies can be routed back to the right device.

Tunneld uses MASQUERADE, a form of SNAT (source NAT) that automatically uses the outgoing interface's address. This is configured in lib/tunneld/iptables.ex: 

# From lib/tunneld/iptables.ex:
defp internet_passthrough() do
  System.cmd("iptables", [
    "-t", "nat",              # Use the NAT table
    "-A", "POSTROUTING",      # After routing decision, before leaving
    "-o", get_env(:upstream), # On packets going out the upstream interface
    "-j", "MASQUERADE"        # Rewrite source IP to the interface's IP
  ])
end

Ports and Sockets

An IP address identifies a machine, but a machine runs many services. Ports (0-65535) identify which service a packet is for. A socket is the combination of IP address + port that a service binds to and listens on.

When you run ss -tlnp (or netstat), you see listening sockets: 

$ ss -tlnp
State  Recv-Q Send-Q Local Address:Port   Peer Address:Port Process
LISTEN 0      128    0.0.0.0:80            0.0.0.0:*         users:(("nginx",pid=1234))
LISTEN 0      128    127.0.0.1:5432        0.0.0.0:*         users:(("postgres",pid=5678))
LISTEN 0      128    0.0.0.0:22            0.0.0.0:*         users:(("sshd",pid=910))

# 0.0.0.0:80 means "listen on all interfaces, port 80"
# 127.0.0.1:5432 means "listen only on loopback, port 5432"

How Tunneld Uses Networking

Tunneld operates as a dual-homed gateway: one interface faces the internet (upstream), the other faces the local subnet (downstream). It performs several networking functions:

Interface Configuration

Interface names are read from app config, never hardcoded. In production, these come from environment variables set by the installer: 

# config/runtime.exs (prod only - there are NO defaults, a missing env is fatal):
if config_env() == :prod do
  gateway = System.get_env("GATEWAY") || raise "Missing ENV: GATEWAY"
  upstream = System.get_env("UPSTREAM_INTERFACE") || raise "Missing ENV: UPSTREAM_INTERFACE"
  downstream = System.get_env("DOWNSTREAM_INTERFACE") || raise "Missing ENV: DOWNSTREAM_INTERFACE"

  config :tunneld, :network,
    gateway: gateway,
    upstream: upstream,
    downstream: downstream
end

# lib/tunneld/iptables.ex reads these:
def get_env(:gateway), do: Application.get_env(:tunneld, :network)[:gateway]
def get_env(:upstream), do: Application.get_env(:tunneld, :network)[:upstream]
def get_env(:downstream), do: Application.get_env(:tunneld, :network)[:downstream]

Link State

lib/tunneld/net_link.ex reads whether an interface is up or down from the kernel's sysfs interface. The module provides upstream_up?/0 and downstream_up?/0 which return booleans. Internally, it reads from /sys/class/net/<iface>/operstate: 

# From lib/tunneld/net_link.ex:
@operstate_path "/sys/class/net"

defp iface_up?(which) do
  cond do
    mock?() ->
      fake_state(which)

    iface = net_config()[which] ->
      case File.read(Path.join(@operstate_path, "#{iface}/operstate")) do
        {:ok, contents} -> String.trim(contents) == "up"
        _ -> false
      end

    true ->
      false
  end
end

The public API is simple: NetLink.upstream_up?/0 returns true or false. The status/0 function returns a map with both interfaces: 

# From lib/tunneld/net_link.ex:
def status do
  %{
    upstream: %{iface: upstream_iface(), up: upstream_up?()},
    downstream: %{iface: downstream_iface(), up: downstream_up?()}
  }
end

Overlay vs LAN Addresses

The address_for/1 function in lib/tunneld/overlay.ex is the critical decision point: given a machine, should we reach it at its LAN IP or its overlay (WireGuard) IP? 

# lib/tunneld/overlay.ex:
def address_for(machine) do
  if same_subnet?(machine["address"]) do
    machine["address"]         # Local: use LAN IP (e.g., 10.0.0.50)
  else
    overlay_ip_for(machine)    # Remote: use overlay IP (e.g., 10.88.0.5)
  end
end

Why These Choices

Private Subnets

The 10.0.0.0/24 and 10.88.0.0/24 subnets are chosen because they are in the largest private range (10.0.0.0/8), unlikely to collide with home routers (which typically use 192.168.x.x), and provide plenty of address space. The overlay uses a separate subnet so WireGuard traffic does not collide with LAN traffic.

MASQUERADE vs SNAT

MASQUERADE is used instead of SNAT because the upstream interface might have a dynamic IP (DHCP from an ISP). MASQUERADE automatically uses the current IP of the outgoing interface, while SNAT requires specifying a fixed source IP.

Config-Driven Interface Names

Interface names (eth0, enp0s3, etc.) vary by hardware and distribution. Hardcoding them would break on different devices. By reading from config, the same binary runs on any hardware — the installer just sets the right environment variables.

Examples

Check interface link state

# On the gateway:
$ cat /sys/class/net/eth0/operstate
up

$ cat /sys/class/net/eth1/operstate
up

# This is what NetLink.upstream_up?/0 and NetLink.downstream_up?/0 read

View the routing table

# On the gateway:
$ ip route show
default via 192.168.1.1 dev eth0 proto dhcp    # Upstream (to ISP router)
10.0.0.0/24 dev eth1 proto kernel scope link   # Downstream (local subnet)
10.88.0.0/24 dev wg-d4f4632f scope link        # Overlay (WireGuard peers)

# On a device on the subnet:
$ ip route show
default via 10.0.0.1 dev eth0    # All traffic goes to Tunneld gateway
10.0.0.0/24 dev eth0 scope link  # Except local subnet traffic
