18 — Terminal Exec

Key sources: lib/tunneld_web/channels/exec_channel.ex, lib/tunneld/machines/ssh/session.ex, lib/tunneld_web/channels/user_socket.ex

What Terminal Exec Is

Terminal Exec is Tunneld's interactive SSH terminal feature. It streams a full PTY session from a managed machine directly into the browser, letting operators type commands and see output in real time. The architecture is: browser → Phoenix channel → gateway → Erlang :ssh → target machine. The browser never touches the SSH connection directly; all credentials stay on the gateway.

Unlike the POST /machines/:id/exec API endpoint which runs a single command and returns output, the terminal maintains a persistent interactive session. The operator sees a real shell prompt, can run htop, vim, or any interactive program. Resize events propagate through the channel so the PTY dimensions stay in sync with the browser window.

The frontend uses xterm.js, a terminal emulator written in TypeScript. The gateway uses Erlang's built-in :ssh module (shipped with OTP) to open a connection and allocate a PTY. Data flows bidirectionally over a Phoenix channel: keystrokes from the browser are sent as "data" pushes, and output from the remote shell is base64-encoded and pushed as "data" events to the browser.

Security is enforced at two points: socket connect and channel join. The operator must have a valid dashboard session (verified from the HttpOnly cookie). The SSH keys that authenticate to the target machine never leave the gateway; the browser only sees terminal I/O. Session open and close events are logged to the audit log, but individual commands within the session are not captured — an honest limitation documented below.

How It Works

The Channel Flow

When the operator clicks "Terminal" on a machine card, the LiveView renders a hook element with data-machine-id. The TerminalHook JavaScript mounts, creates an xterm.js terminal, and opens a Phoenix socket to /ws. It then joins the channel exec:<machine_id>.

On the server, TunneldWeb.ExecChannel.join/3 verifies the session, looks up the machine, and starts a linked Tunneld.Machines.SSH.Session GenServer. That GenServer calls :ssh.connect/4 to the target (via the WireGuard overlay address), allocates a PTY, and starts a shell. The channel pushes "connected" to the browser, which focuses the terminal.

From then on, keystrokes flow browser → channel → GenServer → SSH connection, and output flows SSH connection → GenServer → channel → browser. The GenServer receives {:ssh_cm, conn, {:data, channel_id, type, data}} messages from the Erlang SSH library and forwards them to the channel via send/2.

PTY and Window Change

When the terminal resizes (the user drags the modal or browser window), the frontend sends a "resize" push with cols and rows. The channel calls Session.resize/3, which issues a :ssh_connection.window_change/6 to the target. This keeps the remote PTY in sync with the browser terminal, so full-screen programs render correctly. 

# From lib/tunneld/machines/ssh/session.ex:
def handle_cast({:resize, cols, rows}, %{connection: conn, channel_id: channel_id} = state)
    when not is_nil(conn) do
  # Send window change (resize) to the PTY
  :ssh_connection.window_change(conn, channel_id, cols, rows, 0, 0)
  {:noreply, %{state | cols: cols, rows: rows}}
end

Cleanup

When the channel terminates (user closes the modal, navigates away, or the connection drops), the ExecChannel.terminate/2 callback stops the SSH session GenServer. The GenServer's terminate/2 closes the SSH connection and removes the temporary user_dir containing the private key copy.

How Tunneld Uses It

Authentication: Two Layers

The socket (TunneldWeb.UserSocket) requires a valid session. The channel (TunneldWeb.ExecChannel) re-checks the session and verifies the machine exists. Both layers must pass. A terminal is remote code execution as root; skipping either check would be catastrophic. 

# From lib/tunneld_web/channels/exec_channel.ex:
def join("exec:" <> machine_id, params, socket) do
  client_id = socket.assigns[:client_id]

  # SECURITY: Verify the operator has a valid dashboard session.
  # This is critical - a terminal is remote code execution as root.
  unless client_id && AuthSession.valid?(client_id) do
    Logger.warning("Unauthorized exec channel join attempt for machine #{machine_id}")
    {:error, %{reason: "unauthorized"}}
  else
    ...
  end
end

SSH via user_dir

Erlang's :ssh.connect/4 authenticates using keys in a user_dir directory. The Session GenServer creates a temporary directory with the machine's private key copied in as id_ed25519 (mode 0600). This is cleaned up on termination. 

# From lib/tunneld/machines/ssh/session.ex:
defp setup_user_dir(key_path) do
  nonce = :crypto.strong_rand_bytes(8) |> Base.encode16(case: :lower)
  user_dir = Path.join(System.tmp_dir!(), "tunneld_ssh_#{nonce}")

  try do
    File.mkdir_p!(user_dir)
    File.chmod!(user_dir, 0o700)

    # Copy the private key as id_ed25519
    dest = Path.join(user_dir, "id_ed25519")
    File.cp!(key_path, dest)
    File.chmod!(dest, 0o600)

    {:ok, user_dir}
  rescue
    e -> {:error, {:user_dir_setup_failed, Exception.message(e)}}
  end
end

Audit Logging

Every session open and close is logged via Tunneld.Audit.log/4. The log includes the machine ID, result (started/closed/failed), and the operator's client ID. This creates an audit trail of who had shell access to which machine and when.

Honest limitation: Individual commands within the PTY session are not captured. Unlike POST /machines/:id/exec, where the command string is logged, an interactive session streams raw terminal I/O. Logging that would require parsing escape sequences and reconstructing lines, which is fragile and privacy-invasive. Tunneld logs session boundaries only.

Why (And Three Bugs Found in Production)

Why a Browser Terminal

The dashboard already manages machines. Adding a terminal means operators never leave the browser to SSH in manually. They do not need to know the overlay IP, do not need the private key on their laptop, and do not need to punch through firewall rules. The gateway handles all of that.

Bug 1: user_dir vs. Key Callback

An earlier version used a custom :key_cb callback to provide the private key to Erlang's :ssh client. It negotiated SSH fine, then failed during userauth for OpenSSH-format ed25519 keys. The error was cryptic: :no_auth_method. Switching to user_dir containing id_ed25519 (mode 0600) worked immediately.

Lesson: Prefer the library's standard mechanism over a bespoke callback. The key_cb interface is designed for HSMs and custom key formats, not for reading a file that the library already knows how to read. The user_dir path is battle-tested and handles OpenSSH format correctly.

Bug 2: _csrf_token Required for Session

Phoenix only populates connect_info[:session] when the socket handshake includes a valid _csrf_token parameter. Without it, connect_info.session is nil, and the socket connect function refused with 403 (no client_id to validate).

The fix was simple: pass the CSRF token from the meta tag when creating the socket. LiveView's own socket does the same thing; this is documented behaviour, just easy to overlook. 

// From assets/js/terminal_hook.js:
const csrfToken = document
  .querySelector("meta[name='csrf-token']")
  ?.getAttribute("content");

const socket = new window.Phoenix.Socket("/ws", {
  params: { _csrf_token: csrfToken },
});

Lesson: A unit test that hand-builds connect_info tests your function, not the framework's delivery of it. The real socket transport populates session only under specific conditions. Integration tests through the actual websocket handshake catch this; unit tests do not.

Bug 3: phx-update="ignore"

xterm.js injects its own DOM into the hook element: a viewport, a canvas, cursor layers. Without phx-update="ignore" on the container, LiveView's next diff reconciled that subtree back to the empty server-rendered div. The terminal silently vanished a few seconds after mounting.

Lesson: Any JS-managed DOM subtree must be excluded from LiveView patching. The phx-update="ignore" attribute tells LiveView to leave the element alone after the initial render. This is required for any third-party library that manipulates the DOM: maps, charts, editors, terminals.

Debugging SSH connection issues

# Common errors and their meanings:

# 1. "Connection refused"
#    - sshd not running on target, or wrong port
#    - Check: ssh -p 22 root@10.100.0.5

# 2. "Host unreachable"
#    - WireGuard overlay not established
#    - Check: ping 10.100.0.5 from gateway

# 3. "SSH key not found for this machine"
#    - Key file missing in TUNNELD_DATA/ssh/<machine_id>
#    - Re-enroll the machine to regenerate keys

# 4. "Failed to allocate PTY"
#    - Target sshd configured with "PermitTTY no"
#    - Check /etc/ssh/sshd_config on target

# 5. Session connects but terminal is blank:
#    - Check browser console for WebGL errors
#    - The renderer falls back to canvas, then DOM
#    - If all fail, check xterm.js version compatibility

Terminal hook initialization with accelerated rendering

// The terminal hook attempts WebGL first, then canvas, then DOM:

loadAcceleratedRenderer() {
  if (!this.term) return;

  const WebglAddon = WebglMod?.WebglAddon || WebglMod?.default?.WebglAddon;
  const CanvasAddon = CanvasMod?.CanvasAddon || CanvasMod?.default?.CanvasAddon;

  // Try WebGL first for best performance
  if (WebglAddon) {
    try {
      const webglAddon = new WebglAddon();
      webglAddon.onContextLoss(() => {
        console.warn("Terminal: WebGL context lost, falling back to canvas");
        webglAddon.dispose();
        this.loadCanvasRenderer(CanvasAddon);
      });
      this.term.loadAddon(webglAddon);
      this.rendererAddon = webglAddon;
      return;
    } catch (e) {
      console.warn("Terminal: WebGL not available:", e.message);
    }
  }

  // Fall back to canvas, then DOM (the default)
  this.loadCanvasRenderer(CanvasAddon);
}
