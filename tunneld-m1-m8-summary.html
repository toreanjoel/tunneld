The core idea

"A resource is an address, not a container. Tunneld never asks what runtime this is — it asks what is listening?"
Discovery

One command enumerates everything

A single ss -tlnp lists every listening socket and owning process on any Linux host — whether it's Docker, Incus, systemd, a tmux'd Go binary, or a runtime not yet invented.

Two installs, ever

WireGuard + Caddy

Tunneld installs exactly two things on a target. Anything else is "the operator SSHes in and does it." No Ansible-with-a-worse-UI.

Second idea

WireGuard makes remote machines local

Today location forked the codebase. Once every machine is a WireGuard peer, both are "an IP tunneld can route to." location survives only inside address_for/1.

Consequence

Provider deleted

All Incus CRUD removed. Containers stay visible (they listen on ports) but are no longer managed.

Non-negotiable principles applied

  • Idempotence — every op is ensure_*; re-running converges. Killed reopen-on-boot logic.
  • Namespace ownership — tunneld owns exactly one `tunneld-*` namespace per concern per machine.
  • Remote state is authoritative — disk is a hint.
  • Reconcile over repair — one reconcile/1 reads live state and diffs.

M1 — Caddy on the gateway

Replace nginx reverse proxy with a Caddy instance driven entirely through its JSON admin API. 4 commits.

New

Tunneld.Caddy

  • sync/1 reconciles the entire config from the resource list — idempotent, no per-resource add/remove.
  • Config loaded via POST /load (PUT /config/ 409s on existing config).
  • Per-server automatic_https.disable=true so Caddy never binds :80 (owned by tunneld).
Planes

LAN + Loopback

One :18000 server routes by Host header (<name>.tunneld.lan); each resource also gets a unique 127.0.0.1:2xxxx listener with no host matcher (for zrok/cloudflared/manual).

Example — what a resource becomes in Caddy

{ "apps": { "http": { "servers": {
  "tunneld_lan": { "listen":[":18000"],
    "routes":[{"match":[{"host":["app.tunneld.lan"]}],
      "handle":[{"handler":"reverse_proxy",
        "upstreams":[{"dial":"10.0.0.5:3000"}]}]}],
    "automatic_https":{"disable":true} },
  "tunneld_123_loop": { "listen":["127.0.0.1:20001"],
    "routes":[{"handle":[{"handler":"reverse_proxy",
      "upstreams":[{"dial":"10.0.0.5:3000"}]}]}],
    "automatic_https":{"disable":true} }
}}}}}

Also: opened :18000 in the gateway iptables (INPUT policy is DROP); installer swaps nginx → Caddy; services monitor keyed off :caddy.

M2 — Runtime discovery layer

The "what is listening?" generalization. Discovery, not management. 1 commit.

New

Tunneld.Machines.Runtime

  • listeners/1 — runs ss -tlnp, parses into %{addr, port, proc, pid, container}.
  • Annotates the owning container only if a runtime is detected (incus/docker/podman) — never gated on one.
  • probe/1 — generic: OS, kernel, arch, CPU, RAM, detected_runtimes. No Incus fields.
Surface

Listeners → resource

Machine detail shows a Listeners panel with a per-row "make resource" action that promotes any listener to a Caddy resource. Backend routed via Overlay.address_for/1.

Example

GET /api/v1/machines/:id/listeners
→ {"listeners":[
    {"addr":"0.0.0.0","port":22,"proc":"sshd","pid":1140,"container":null},
    {"addr":"0.0.0.0","port":3000,"proc":"node","pid":5678,"container":null}
  ]}

Live-verified: a bare VM running only sshd appears in listeners — a bare box with no container runtime works identically.

M3 — Overlay (WireGuard) + Expose deletion

WireGuard makes remote machines local. 5 commits; net −146 lines.

New

Tunneld.Overlay

  • Gateway dials out to each VM (PersistentKeepalive=25), one iface wg-<id>.
  • Table = off — tunneld installs routes by hand (prevents loops; prerequisite for egress).
  • Keys generated on gateway, stored mode 0600 under TUNNELD_DATA/wg/; target only gets its half.
  • address_for/1 — the single place location is branched: LAN IP same-subnet, overlay IP remote.
Deleted

Machines.Expose (SSH -L tunnels)

The SSH -L tunnel layer is gone, replaced by the overlay. This also removed bugs §3.2 (tunnel leak on restart) and §3.3 (failed exposures persisted) by deletion. Quick Expose (LAN device curl endpoint) kept.

Live acceptance (after Vultr opened UDP/51820)

  • ✓ Resource overlayapp with backend 10.88.0.2:8080 (overlay IP) serves OVERLAY-SERVICE-OK at http://overlayapp.tunneld.lan:18000.
  • ✓ No SSH tunnel process anywhere — ps aux | grep 'ssh.*-L' → NONE.
  • ✓ Reboot-survives — rebooted the gateway; after reboot WG iface up with a fresh handshake, resource still serves, no orphaned processes.

M4 — Remote Caddy + public exposure

Drive the machine's own Caddy over the overlay; expose services on the public internet. 1 commit.

New

Public/remote plane in Caddy

  • build_public_config/1 + sync_public/2 push a config to the machine's Caddy admin API at http://<overlay_ip>:2019 over WireGuard.
  • Admin endpoint bound to the overlay address only — never 0.0.0.0, never public.
One field

listen = port | hostname

Same object, one field, no migration: "8080" → no domain/TLS; "app.example.com" → :80/:443 with auto-TLS. Point DNS, change one field, done.

Example — the listen-field transition

listen "8080"  → server listen [":8080"], no host matcher, automatic_https.disable=true
listen "app.example.com" → server listen [":80",":443"],
    route match host app.example.com, automatic_https (default = auto-TLS)

Live-verified: installed Caddy on the VM (admin on 10.88.0.2:2019 over overlay), gateway pushed a no-domain/TLS config (HTTP 200), VM Caddy served :8081 proxying to the backend. Public internet reachability of the port needs Vultr inbound TCP open (like UDP/51820 was).

M5 — Agent API (the product)

The HTTP API is the product; CLI/skill/MCP are thin adapters with no policy. 4 commits.

New

AgentTokens / Audit / Jobs

  • AgentTokens — scoped, revocable, hashed-at-rest tnld_... bearer tokens. Raw token returned once; only SHA-256 stored. Forbidden scopes (token issuance, enrollment, iptables admin, DNS provider, WG keys) can never be granted.
  • Audit — append-only JSONL (ts, token_id, action, target, result).
  • Jobs — long ops (probe/exec) return 202 {job_id}; poll /jobs/:id.
Contract

Scoped routes

MethodPathScope
GET/machinesmachines:read
POST/machines/:id/execexec
GET/POST/DELETE/resourcesresources:*
POST/machines/:id/probemachines:write
GET/jobs/:idany (any valid token)

Example — exec + job

POST /api/v1/agent/machines/:id/exec {"cmd":"echo hi"}  → 202 {"job_id":"962","status":"running"}
GET  /api/v1/agent/jobs/962 → 200 {"id":"962","status":"done","result":"{...}"}

Live-verified: 200 on machines/resources, 201 resource create via real Caddy path, 202 exec → JSON-safe job, 401 missing token, 403 insufficient scope. Two live bugs fixed (any-scope jobs, JSON-safe results).

M6 — Egress (per-device exit routing)

Route a subnet device's traffic out through a managed machine instead of the gateway's own upstream. 1 commit.

How it works
# per exit machine: one routing table
ip route add default dev wg-<machine_id> table <N>
ip rule add from <device_ip> lookup <N>
# adding/removing a device is one ip rule
# on the exit machine:
sysctl net.ipv4.ip_forward=1  (persistent)
iptables -t nat -A POSTROUTING -o <iface> -j MASQUERADE

Table IDs allocated from a persisted map (never recomputed from a hash). Works only because tunneld is the DHCP default gateway — asserted at runtime with a clear error otherwise. DNS leaks handled as an explicit choice (dns: "exit" | "local"), never silently.

Example

route_device(exit_machine, "10.0.0.100")
→ {:ok, %{device_ip:"10.0.0.100", machine:id, table:"100", dns:"local"}}
unroute_device(exit_machine, "10.0.0.100")   # one delete reverts

M7 — Reconcile, Disenroll, UI polish

Drift detection, fully-reversible enrollment teardown, and new dashboard surfaces. 5 commits.

Reconcile

One live-state authority

reconcile/1 reads live state (WG, Caddy, SSH) and diffs against desired; repair: true idempotently fixes drift (e.g. re-ensure_peer when a remote WG iface is down). Replaces ad-hoc reopen-on-boot.

Disenroll

Reverse teardown

Removes only tunneld-owned artifacts: WG config/unit/iface, iptables TUNNELD chain, the tunneld authorized_keys entry, then the registry record + SSH key.

M7 disenroll — live-verified on target

After removing a test machine, verified on the VM by hand: authorized_keys tunneld entries=0, WG confs=0, interfaces=0, TUNNELD iptables chain=0.

UI polish

  • Machine detail: Reconcile button + Overlay IP / WireGuard status panel (verified headless-browser, no console errors).
  • Device row: egress dropdown (Local or any exit-capable machine) wired to Egress.route_device.

M8 — Adapters (CLI → skill → MCP)

Thin adapters over the agent HTTP API; the API is the product. Build order API → CLI → skill → MCP. 4 commits + gitignore.

CLI

mix tunneld.agent

Machines, listeners, probe, exec, jobs, resources, add/rm-resource. Reads TUNNELD_URL + TUNNELD_TOKEN.

Skill

skill/SKILL.md + tunneld_agent.py

Thin Python client (~95 lines). Verified end-to-end against a live gateway (create/read/remove resource via real Caddy path).

MCP

tunneld_mcp.py

MCP JSON-RPC over stdio, 9 tools, one per endpoint, no policy. Verified: tools/list + tools/call created a resource.

Example

export TUNNELD_TOKEN=$(mix tunneld.issue_token machines:read,resources:write,exec)
mix tunneld.agent machines
mix tunneld.agent add-resource myapp 10.0.0.5:3000
mix tunneld.agent exec <id> "systemctl status app"

How to run & use it

Issue a scoped token (operator, on the gateway)

mix tunneld.issue_token machines:read,resources:write,exec
# TOKEN: tnld_...

Use the CLI

export TUNNELD_URL=http://10.0.0.1 TUNNELD_TOKEN=tnld_...
mix tunneld.agent machines
mix tunneld.agent listeners <machine_id>
mix tunneld.agent add-resource web 10.0.0.5:3000

Use the skill / MCP

from tunneld_agent import TunneldClient
c = TunneldClient()
print(c.resources())
# MCP: python skill/tunneld_mcp.py  (stdio JSON-RPC)

Local dev (no SBC)

MOCK_DATA=true mix phx.server   # full flow on a laptop
